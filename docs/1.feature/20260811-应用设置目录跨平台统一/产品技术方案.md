# 应用设置目录跨平台统一（`~/.apicase`）

## 需求

应用级设置（`settings.json`）现在按各平台的系统约定存放：

| 平台 | 现位置 |
|---|---|
| macOS | `~/Library/Application Support/com.apicase.app/settings.json` |
| Linux | `$XDG_CONFIG_HOME/com.apicase.app/settings.json`（缺省 `~/.config/...`） |
| Windows | `%APPDATA%\com.apicase.app\settings.json` |

三条路径互不相同、都很长，**记不住**：想手改一下配置、想在另一台机器上找同一个文件、
想在文档里写一句「配置在哪」，每次都要先查是什么系统。

改为**三平台同一个位置**：

```
~/.apicase/settings.json
```

Windows 上即 `C:\Users\<用户名>\.apicase\settings.json` —— 写法与 macOS / Linux 完全一致，
一句话说得清。这也是开发者工具的通行做法（`~/.ssh`、`~/.aws`、`~/.docker`、`~/.gitconfig`）。
apicase 本就是一个开发者工具，配置目录该像开发者工具，而不是像一个 GUI 应用。

顺带解决两件事：

- **`APICASE_HOME` 可覆盖**：CI、容器、便携安装需要把配置钉在指定目录；
  测试也不必再去改 `HOME`（进程全局，并行跑会互相抹）。
- **Windows 上没有 `HOME`**：现有 `home()` 只读 `HOME`，Windows 上基本取不到——
  此前 Windows 走的是 `APPDATA` 分支所以没暴露，换成主目录后必须补 `USERPROFILE`。

## 兼容：老用户的设置不能丢

新位置一律优先，旧位置作为**迁移来源与只读回落**：

- **桌面端读设置时迁移**（`read_app_settings`）：新文件不存在且旧文件存在 → 搬过去
  （`rename`，跨卷失败则复制后删原文件），随后尝试删掉空的旧目录。
  桌面端是这个文件的主人（唯一会写它的一端），迁移只在这里做一次。
- **CLI 只回落读，不写盘**（`load_app_prefs`）：新文件读不到就读旧文件。
  CLI 可能跑在只读环境 / CI 里，它不该有搬文件的副作用；桌面端跑过一次后自然就统一了。
- 一切失败照旧**静默回落默认**，绝不报错——只用 CLI 的人本来就没有这个文件。

## 执行计划

1. `app/core/src/paths.rs`
   - `APP_DIR_NAME = ".apicase"`；`app_config_dir()` = `home()/.apicase`，
     `APICASE_HOME`（绝对路径）优先。
   - `home()` 补 Windows 的 `USERPROFILE` / `HOMEDRIVE`+`HOMEPATH`。
   - 保留 `legacy_app_config_dir()` / `legacy_app_settings_file()`（原 Tauri 语义的三平台分支）。
   - `load_app_prefs()` 新→旧回落读；新增 `migrate_legacy_settings()` 供桌面端调用。
   - 测试：路径形状、`APICASE_HOME` 覆盖、迁移行为、回落读。
2. `app/src-tauri/src/commands/app.rs`
   - `read_app_settings` 先调 `migrate_legacy_settings()`。
   - 删掉 `core_config_dir_matches_tauri`（不再对齐 Tauri 的 `PathResolver`，那正是要摆脱的东西），
     换成断言新位置形状的测试。
   - 注释更新。
3. `app/src/settings.ts`、`app/src/App.tsx` 注释里的示例路径更新。
4. 文档同步 `docs/0.latest/`（`0.概览.md` 加条目、`2.技术架构.md` 更新路径表述）。
