# 并行度设置

_2026-08-12_

## 一、需求

设置页增加「并行度」一项，并让应用**真的按这个值并发跑**——桌面端批量运行、CLI、MCP 三端同一个来源。

在此之前：执行内核（`core/src/runner.rs`）早就支持 `concurrency > 1`（信号量限流 + `JoinSet`，
有单测钉住），但**没有任何入口能把这个值调起来**：

| 入口 | 现状 |
| --- | --- |
| 桌面端批量运行 | `batchRunOpts()` 里硬编码 `concurrency: 1` |
| CLI `apicase run` | `-j` 默认 1，不读工作空间配置 |
| MCP `apicase_run` | `p.concurrency.unwrap_or(1)` |

于是「引擎能跑并发」这件事对用户不存在。本期把这条链接通。

## 二、设计决定

### 1. 放工作空间设置（`application.yml` 的 `settings:`），不放应用设置

设置页的导航分两组：上＝跟随**项目**（`application.yml`），下＝跟随**应用**（`~/.apicase/settings.json`）。
并行度归上面那组，理由：

- **它是被测服务的属性，不是这台机器的属性。** 「这套接口能扛多少并发回归」由服务端决定，
  换台电脑不会变；而团队里每个人都该按同一个值跑，否则「我这儿过了你那儿挂」查不出根因。
- **随 git 走，CI 与本地一致。** CLI 在 CI 里不带 `-j` 就用项目配置，与桌面端点「运行」跑出的是同一件事。
- 同一分区里已有语义同类的 `continueOnAssertionFailure`（失败传播策略），它当初也是按这条理由放进来的。

落在 `settings.concurrency`，与既有键平级：

```yaml
settings:
  concurrency: 4        # 用例之间的并发数；1 = 串行（默认，不落盘）
```

### 2. 默认仍是 1（串行）

不改变既有行为。并发把「跑得慢」换成了「跑得快但顺序不确定、被测服务压力 × N」，
这个交换该由用户显式做出，而不是升级一次版本就被动接受。默认值不落盘（同其它设置项）。

### 3. 上限 64，解析期 clamp

`MAX_CONCURRENCY = 64`。手滑把 `4` 写成 `400` 的代价不是「慢一点」，而是几百条连接同时打到
被测服务上——那是一次压测，不是一次回归。解析期 clamp 而不是报错：配置容错的既有约定是
「认不出就回落，绝不抛错」（见 `parse_settings` 的文档）。

### 4. 三端同一个来源，命令行参数是**临时覆盖**

`Workspace::run_opts()` 统一把 `settings.concurrency` 装进 `RunOpts`，三端都走它。
`RunRequest.concurrency` 由 `u32` 改成 `Option<u32>`——`None` = 跟随工作空间设置，
`Some(n)` = 这一次覆盖它。这与同一结构里 `continue_on_assertion_failure: Option<bool>`
的语义完全一致，不引入第二套规则。

CLI 的 `-j/--concurrency` 因此也变成「不给就跟配置走」。

### 5. 调试运行不受影响

界面上点「发送 / ▶ 运行全部」跑的是**一个 case 内部的 step**，恒按拓扑序串行——
step 之间有 `dependsOn` 与 outputs 传递，并发跑没有意义。并行度只作用于**case 之间**。
`debugRunOpts()` 保持 `concurrency: 1`。

## 三、并发下的正确性

`concurrency > 1` 时 case 之间真并发。既有的三条保证已经覆盖了共享状态：

- **变量隔离**：每个 case 一份独立 `RunContext`，case 之间不共享 outputs（`runner.rs` 模块文档第一条不变量）。
- **OAuth 2.0 token 缓存**：按缓存键做了 in-flight 去重（`auth.rs`，有 `oauth2_dedupes_under_concurrency` 钉住）。
- **Cookie jar**：`RwLock<CookieStore>` + `Mutex<WriteState>`，落盘节流最快 1s 一次，收尾 `flush_all()`。
- **HTTP 客户端**：按 `ClientConfig` 缓存，多个 case 共用同一个连接池（并发的收益正来自这里）。
- **进度回调**：并发路径下结果按**完成序**在 `join_next()` 里串行 `push` + `emit`，
  一次回调仍只新增一个 case——桌面端 `run_batch` 的增量事件（取 `cases[n-1]`）因此不受影响。

## 四、执行计划

### core

1. `model.rs`：`WorkspaceSettings` 加 `concurrency: u32`，`Default` 给 1；导出 `MAX_CONCURRENCY`。
2. `yaml/mod.rs`：
   - `parse_settings` 解析 `concurrency`（非数字 / < 1 / 超上限 → clamp 到 `1..=64`）；
   - `MANAGED_SETTING_KEYS` 补一项（漏了会导致「界面上改了、文件里没变」）；
   - `ser_settings` 在 `> 1` 时落盘。
3. `workspace.rs`：`run_opts()` 把 `settings.concurrency` 装进 `RunOpts`。

### CLI / MCP

4. `cli.rs`：`-j` 改 `Option<u32>`，帮助文案改成「省略 = 跟随工作空间设置」。
5. `ops/run.rs`：`RunRequest.concurrency: Option<u32>`，`Some` 才覆盖。
6. `mcp.rs`：`p.concurrency` 直接透传（本就是 `Option`）。

### 桌面端

7. `case.ts`：`WorkspaceSettings` 与 `DEFAULT_WS_SETTINGS` 加 `concurrency`。
8. `run.ts`：`batchRunOpts()` 增加 `concurrency` 入参（默认 1，clamp 到 `1..=64`）。
9. `App.tsx`：
   - 设置页「运行」区加数字输入（1–64，说明并发只作用于 case 之间）；
   - `startRun()` 把 `wsSettings.concurrency` 递下去——报告头的 `options.concurrency` 从 `opts` 派生，自动带上。

### 测试

10. `yaml/tests.rs`：解析容错（负数 / 超限 / 非数字）、默认不落盘、往返一致。
11. `workspace.rs` 测试：配置 → `RunOpts.concurrency`。
12. `cli.rs` 测试：`-j` 省略即 `None`。
