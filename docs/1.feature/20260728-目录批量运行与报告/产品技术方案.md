# 目录批量运行与报告

> 在文件树对目录（或单个用例）发起**批量回归运行**，应用内实时看进度，同时在工作空间落一份**单文件自包含 HTML 报告**——脱离 apicase、任意有浏览器的地方都能打开。

## 一、需求内容

当前 apicase 只有**调试运行**：打开一个 case，点「发送 / ▶ 运行」，在响应区看结果。缺的是**回归运行**——把一个目录下的一批用例跑一遍，拿到一份可归档、可分发的结果报告。

### 1.1 先区分两个概念

这是整个方案的地基。两者不是"多跑几个"的量差，是目标不同：

| | 调试运行（已有） | 回归运行（本期） |
|---|---|---|
| 目标 | 一个 case | 一组 case（目录 / 单文件） |
| 关注 | 响应内容长什么样 | 通过率 + 失败原因 |
| 产物 | 界面上的响应区 | 一份可归档、可分发的报告 |
| 变量 | 共享当前编辑态 | 每个 case 独立隔离 |
| 中断 | 无所谓 | 必须可取消、可续看 |

因此**右键菜单不能只加一个「运行」**——文件上"运行"= 打开界面跑、目录上"运行"= 出报告，同一个词做两件事，用户点第二次就会困惑。两项分开：

- **「打开并运行」**（仅文件）＝ 打开标签 + 自动发送，即现有调试路径的快捷方式。
- **「运行并生成报告…」**（文件与目录都有）＝ 本期主体。**文件上也要有**——跑单个 case 出报告是合理需求，且让"报告"这条路径从集合大小 1 开始就统一，没有特例分支。

### 1.2 哪些运行会留下报告

**判据是用户的意图，不是目标的数量。**

| 触发方式 | 落报告 | 理由 |
|---|---|---|
| 右键「运行并生成报告…」（目录） | ✅ | 明确要记录 |
| 右键「运行并生成报告…」（单个 case） | ✅ | 同上，集合大小为 1 不是特例 |
| 请求编辑器里点「发送 / ▶ 运行」 | ❌ | 只是想看看响应长什么样 |

调试运行**不进报告历史**，混进来有三个具体后果：

- **淹没**：调一小时点几百次发送，真正的回归记录被冲掉。
- **写盘开销**：每点一次发送就渲染 + 写一个 HTML，调试手感变差。
- **语义错位**：单个 step 的"报告"，概览卡片写「总数 1 / 通过 1」很滑稽。

Postman 也是分开的——History 面板（调试）与 Collection Runner results（回归）是两个东西，Insomnia 同理。

**调试历史本身是该有的**（`docs/0.latest/0.概览.md` 路线图里"历史"已列），但它的正确形态是轻量的**响应历史**：每个请求保留最近 N 次响应、会话级或轻持久化、不落 HTML——属另一个需求。真要合并展示，正确做法也是**两个视图**而非一个混合列表。

**逃生口（本期不做）**：响应区可加一个「保存为报告」，把当前这次调试结果按需落成一份正式报告。按需触发、不自动写，两种历史的边界不被破坏。

### 1.3 交互流程

```
右键目录 / 文件 → 「运行并生成报告…」
   ↓
运行配置对话框（列出将要运行的用例 + 递归开关 + 环境选择）
   ↓
新开一个「运行报告」标签页 → 实时逐条追加结果，可取消
   ↓
同时周期性写盘 <workspace>/.apicase/reports/<时间戳>/report.html
```

### 1.4 运行配置对话框

| 项 | 本期 | 说明 |
|---|---|---|
| **将要运行的用例** | ✅ | 列出匹配到的 N 个 case（含被跳过的及原因）。**必做**——Newman / Bruno 都没有，结果是用户常不知道自己刚跑了什么 |
| **递归子目录 / 仅当前目录** | ✅ | 目标是目录时才显示；默认递归 |
| **环境** | ✅ | 默认当前活动环境，可切。回归常需指定 test / prod，不该强绑 topbar 的选择 |
| 并发度 | ❌ 本期不做 | 默认串行（`concurrency: 1`）。runner 留参数位，将来加调度器不改签名 |
| 失败后停止 | ❌ 本期不做 | 默认失败继续——批量运行要的是完整报告 |
| 输出目录 / 报告格式 | ❌ 本期不做 | 固定默认路径、固定 HTML |

**用例发现规则**：`.yml` / `.yaml` 且非 `application.yml`；`analyzeCase` 判定无效的记为 `skipped` 并在报告中列出原因（不静默丢弃——静默跳过会让人误以为全跑过了）；沿用 `search_workspace` 的遍历约定（跳过隐藏项与 `node_modules` / `target` / `dist`）。**执行顺序按文件路径排序**，可预期、可控（用户用 `01-` / `02-` 前缀即可编排顺序）。

## 二、核心架构：执行 → 结果数据 → 渲染器

**三层，不是两层。** 业界（Allure / Playwright / Newman）都是这个分层：

```
runner.ts            执行 → 产出 RunReport（纯数据）
    ↓
report/html.ts       RunReport → 单文件 HTML（内联 JSON 数据）（本期）
    ↑
    └─ parseReportHtml(text) → RunReport                      （本期，反向读回）

report/junit.ts      RunReport → JUnit XML                     （后续，接 CI）
```

**不边跑边拼 HTML 字符串。** 执行只产出结构化的 `RunReport`，渲染是纯函数 `render(report) → string`。三点收益：

1. 加格式 = 加一个 renderer 文件，执行引擎一行不改。
2. 渲染器是纯函数 → 直接单测（喂构造的 RunReport，断言输出），契合本仓库既有的 `test/*.test.mjs` 风格。
3. **将来做 `apicase run` CLI 接 CI 时，`RunReport` 就是现成的契约。** 这才是批量运行的终极形态，schema 现在就要为它留位置。

### 2.1 只落一份 `report.html`——数据就在它里面

单文件自包含的设计**本来就要把 `RunReport` 内联进 HTML**（`<script id="apicase-report" type="application/json">`），所以再单独落一份 `report.json` 是**同一份数据存两遍**。

### 2.2 报告只有一套渲染实现（apicase 内外像素级一致）

**这是本方案的一条硬约束。** 若 apicase 里用 React 组件渲染、分发出去的 HTML 里用内联 JS 渲染，就是**两套实现渲染同一份数据**——改一次配色改两处、加一个字段改两处，时间一长必然漂移，用户在 apicase 里看到的和发给同事的不是同一个东西。这不是"注意维护"能兜住的，是结构问题。

故 **apicase 内也用 iframe 嵌同一份报告页面**，关键在于分层划对：

```
┌─ 运行报告标签页 ──────────────────────────────┐
│ ████████░░░░ 12/45 ✓10 ✗2  [取消] [浏览器打开] │  ← apicase 原生工具栏（iframe 外）
├──────────────────────────────────────────────┤
│   <iframe sandbox="allow-scripts">           │  ← 报告内容（iframe 内）
│     与分发出去的 HTML 出自同一模板             │     唯一一套渲染实现
└──────────────────────────────────────────────┘
```

| 层 | 内容 | 归属 |
|---|---|---|
| **iframe 内** | 概览卡片、结果列表、折叠、筛选、搜索 | 报告本体，apicase 内外完全一致 |
| **iframe 外** | 进度条、取消、在浏览器打开、导出 | **运行控制**——分发出去的 HTML 里本就不该有"取消"按钮 |

之前把这两层混在一起，才会得出"apicase 内必须原生渲染"的错误结论。划开之后，`RunReportPane` 从"完整结果树组件"缩成"iframe 壳 + 工具栏 + postMessage 收发"，**工作量反而更小**。

#### 宿主与报告页的通信协议

live 运行时**不重塞 `srcdoc`**（整页重画会丢滚动位置与展开状态），改为 `postMessage` 推数据、iframe 内按 case id 增量更新 DOM。live 与历史因此走同一条路径——都是「空壳 + 推数据」：

| 方向 | 消息 | 说明 |
|---|---|---|
| 宿主 → 报告 | `{type:'host', app:'apicase'}` | 握手。**收不到即为浏览器独立打开**，IDE 专属动作自动隐藏 |
| 宿主 → 报告 | `{type:'theme', mode:'light'\|'dark'}` | 主题跟随 apicase（浏览器下回落 `prefers-color-scheme`） |
| 宿主 → 报告 | `{type:'report', report}` | 全量 / 增量数据 |
| 报告 → 宿主 | `{type:'open-case', file, stepId}` | 点失败用例 → apicase 打开对应 `.yml` 并定位 step |
| 报告 → 宿主 | `{type:'load-request', file, stepId}` | 把失败请求载入请求编辑器重调 |

**IDE 联动因此没有丢**——iframe 内的展示是共享的，iframe 外的动作是 apicase 独有的。`sandbox="allow-scripts"` 且不给 `allow-same-origin`，报告页访问不了父窗口与存储；`srcdoc` 的 origin 是 `null`，故 `postMessage` 用 `'*'` 且**宿主侧只按 `type` 白名单处理、不信任消息内容**（`file` 需校验在工作空间内）。

`renderHtml(report)` = 空壳模板 + 内联数据，iframe 用的就是同一个空壳。历史报告打开时 `parseReportHtml(text)` 切出数据再推——`parseReportHtml(renderHtml(r))` 往返等价的单测是这条链路的护栏。提取失败即视为普通 HTML，走现有纯文本视图。

后续补 **JUnit XML**（GitLab CI / Jenkins / GitHub Actions 全都原生解析，接 CI 的唯一硬通货）；独立 JSON 导出可作为一个"导出为…"动作按需补，不必每次运行都落盘。**YAML 报告不做**——人看 HTML，机器吃 JSON / XML，两头不靠；case 用 YAML 是因为**人要手写**，报告是机器生成的，不适用同一逻辑。

## 三、数据模型 `RunReport`

单一事实源，改动成本最高，现在就定准。

```ts
export interface RunReport {
  schemaVersion: 1;
  tool: { name: "apicase"; version: string };
  startedAt: string;                    // ISO 8601
  finishedAt: string | null;            // 运行中为 null
  durationMs: number;
  status: "running" | "done" | "cancelled";
  workspace: { name: string; root: string };
  environment: { name: string; vars: Record<string, string> };   // 已脱敏
  options: { targets: string[]; recursive: boolean; environment: string;
             concurrency: number; stopOnFailure: boolean; redact: boolean };
  summary: {
    total: number; passed: number; failed: number; error: number; skipped: number;
    assertions: { total: number; passed: number; failed: number };
  };
  cases: CaseResult[];
}

export interface CaseResult {
  file: string;                         // 相对工作空间根
  name: string;                         // case 的 name，缺省用文件名
  status: "passed" | "failed" | "error" | "skipped" | "running";
  skipReason?: string;                  // skipped 时说明（解析失败等）
  startedAt: string; durationMs: number;
  steps: StepResult[];
}

export interface StepResult {
  id: string;
  status: "passed" | "failed" | "error" | "running";
  durationMs: number;
  request:  { method: string; url: string; headers: KVPair[];
              bodyPreview: string | null; bodyBytes: number; truncated: boolean };
  response: { status: number; statusText: string; headers: KVPair[];
              bodyPreview: string | null; bodyBytes: number; truncated: boolean;
              elapsedMs: number } | null;
  outputs: Record<string, unknown>;
  assertions: { target: string; op: string; expected: string; actual: string; ok: boolean }[];
  error?: string;
}
```

**状态语义**：`failed` = 请求发出去了但断言没过；`error` = 请求本身失败（网络 / TLS / 超时 / 变量解析崩了）。两者在报告里要能分辨——前者是被测服务的问题，后者常是环境或用例自身的问题，排查方向完全不同。

### 3.1 脱敏是默认行为，不是选项

报告会被发出去、进 CI 制品、甚至被提交进仓库。**Newman 的 HTML 报告泄露线上 token 是真实发生过的事故。**

- 默认掩码：请求头 `Authorization` / `Cookie` / `Proxy-Authorization`，响应头 `Set-Cookie`，以及名字匹配 `/token|secret|password|passwd|credential|api[-_]?key/i` 的头与环境变量。
- 掩码形式保留前 4 位：`Bearer eyJh…（已脱敏）`——完全抹掉会让"是不是根本没带上认证"无法排查。
- 提供 `redact: false` 的开关（本期不进 UI，只在数据模型与 runner 参数里留位），默认 `true`。

### 3.2 响应体必须截断

单文件 HTML 内联全部响应体，几十个大 JSON 就能把文件顶到几十 MB，浏览器直接卡死。

- 每个请求 / 响应体默认保留前 **64 KB**，超出截断并标注 `已截断，原始 3.2 MB`。
- 二进制响应（复用后端 `read_file_smart` 那套 NUL 嗅探思路判定，或按 Content-Type）只记类型与大小，不存内容。
- `bodyBytes` 记原始大小——截断后仍能看出响应到底多大。

## 四、技术方案

### 4.1 `runner.ts`——执行逻辑从 `App.tsx` 抽出来（本期最关键的重构）

现在 `runRequestWithCtx`（`App.tsx:2727`）闭包捕获了 `proxyConfig` / `requestOptions` / `environments` 等一堆 React state，批量运行没法复用。抽成纯模块：

```ts
export interface RunDeps {
  send: (req: ApiRequest) => Promise<ApiResponse>;   // 注入后端通道
  readFile: (path: string) => Promise<string>;
}
export interface RunOpts {
  environment: { name: string; vars: Record<string, string> };
  concurrency: number;      // 本期恒 1
  stopOnFailure: boolean;   // 本期恒 false
  redact: boolean;          // 本期恒 true
  maxBodyBytes: number;     // 默认 65536
  signal?: AbortSignal;     // 取消
}

export async function runStep(sd: RequestDraft, ctx: RunContext, deps, opts): Promise<StepResult>;
export async function runCase(text: string, file: string, deps, opts): Promise<CaseResult>;
export async function runBatch(files: string[], deps, opts,
                               onProgress: (r: RunReport) => void): Promise<RunReport>;
```

纯函数、不碰 React、依赖全靠注入。**抽完之后调试运行也改走这份**——一份执行语义两处复用，否则"界面里跑过了、批量跑却挂了"这类不一致迟早出现。这也是将来下沉 Rust 做 CLI 时唯一需要移植的模块。

**变量隔离**：每个 case 一份独立 `RunContext`（`{ ...environment.vars, ...case.vars }`），**case 之间不共享 outputs**——outputs 只在 case 内部的 step 间流动（沿用 `onRunAll` 的本地上下文写法）。这条必须写进文档，否则将来一开并发就是竞态。

**取消**：`AbortSignal` 在每个 case 边界检查，当前 in-flight 的请求跑完即停（不中断已发出的 HTTP，避免服务端收到半截请求）。报告 `status` 转 `cancelled`。

### 4.2 `report/html.ts`——单文件自包含 HTML

**为什么是单文件**：诉求是"任意有浏览器的地方打开、不依赖 apicase"。Playwright 的多文件报告在 `file://` 下打不开，官方只能让你 `npx playwright show-report` 起本地服务器——那恰好违背这个诉求。单文件可以直接发微信、当邮件附件、扔进 CI artifacts。

结构：HTML / CSS / JS 全内联，数据挂在 `<script id="apicase-report" type="application/json">` 里，页面 JS 从 `textContent` 读并渲染。

```ts
export const REPORT_SHELL: string;                       // 空壳：CSS + 渲染/交互 JS，无数据
export function renderHtml(report: RunReport): string;   // = 空壳 + 内联数据（落盘用）
export function parseReportHtml(text: string): RunReport | null;  // 反向：切出内联数据
```

**apicase 内嵌用 `REPORT_SHELL` + postMessage 推数据，落盘用 `renderHtml` 内联数据——同一套 CSS 与渲染 JS**，这正是 2.2 那条一致性约束的落地方式。

- **不引入新依赖**：模板字符串拼接；CSS 复用现有设计 token 的取值（4 档圆角 / 6 档字号 / 双主题变量）。
- **主题双通道**：被 apicase 嵌入时听 `{type:'theme'}` 设 `documentElement.dataset.theme`；浏览器独立打开时回落 `prefers-color-scheme`。两条都写进同一份 CSS（`:root[data-theme]` 优先级压过媒体查询），与 apicase 主题体系一致。
- **转义**：响应体可能含 `</script>`，内联 JSON 必须处理（`</` → `<\/`、`U+2028/2029`）。渲染进 DOM 的一律走 `textContent` 而非 `innerHTML`——`markdown.tsx` 已有同类经验可参考。
- **增量更新**：收到 `{type:'report'}` 时按 case `file` 作 key diff 现有 DOM 行，只新增/更新变化的行，**不整页重画**——否则用户展开的详情和滚动位置会在每次进度更新时被重置。
- **交互**：概览卡片（总数 / 通过 / 失败 / 耗时）+ 用例列表（可折叠）+ 每步的请求 / 响应 / 断言详情 + 筛选（全部 / 仅失败）+ 关键字搜索。全部由内联 JS 实现。
- **宿主专属动作**：未收到 `{type:'host'}` 握手时，「在 apicase 中打开此用例」「重新调试此请求」等按钮不渲染——分发给同事的那份点了也没用。

### 4.3 运行中的实时反馈（两件独立的事）

**① 应用内实时——「运行报告」标签页**

复用现有多标签机制。`tabOrder: string[]` 存的是路径，运行相关标签用**伪路径**占位，渲染时按 `apicase://` 前缀分流：

| 伪路径 | 视图 | 说明 |
|---|---|---|
| `apicase://run/<runId>` | `RunReportPane` | 某次运行的报告（live 运行 / 从 `report.html` 读回，两种数据源同一组件） |
| `apicase://runs` | `RunHistoryPane` | 运行历史列表——**本期不做**，伪路径体系先留好位置 |

- 伪路径 → **不走 `openCase`、不进 `tabCacheRef`**——它不是编辑态，`TabSnapshot` 那套字段一个都不需要。运行会话状态单独存 `runSessions: Record<runId, RunReport>`。
- `isDirtyPath` 对伪路径恒 `false`，关闭不弹确认；运行中关闭标签则一并取消运行。
- 多次运行可并存对比（这也是选标签页而非底部面板 / 模态的原因：内容多要滚动，且需要并存）。

`RunReportPane` 的构成（见 2.2 的分层）：

- **原生工具栏**（iframe 外）：进度条 `已完成 12/45 · ✓10 ✗2` + 取消 + 「在浏览器中打开」。
- **iframe**（`sandbox="allow-scripts"`，`srcdoc={REPORT_SHELL}`）：挂载后握手 → 推主题 → 推数据；运行中每有 case 完成即再推一次，iframe 内增量更新。
- **反向消息**：收 `open-case` / `load-request` → 校验路径在工作空间内 → 打开对应 `.yml` 或载入请求编辑器。

**历史报告走同一个组件**——数据源从 live 的 `runSessions` 换成 `parseReportHtml(文件内容)`，只是工具栏没有进度条与取消。一套渲染、一套交互，apicase 内、历史回看、分发出去的三处像素级一致。

**② HTML 文件运行中可看——周期性整份覆写**

> ⚠️ **不要做「HTML 壳 + 增量追加 ndjson + 前端轮询」。** 这是最自然的想法，但在 `file://` 协议下 fetch 同目录文件会被 Chrome / Safari 的 CORS 策略直接拦掉，报告根本加载不到数据。Playwright 正是栽在这里。

替代方案成本几乎为零：每完成一个 case（或每 2 秒节流，取较慢者）调一次 `renderHtml` 整份覆盖写。用户中途用浏览器打开 + 刷新即可看到"运行中，已完成 12/45"的部分结果，结束时最后写一次、状态转 `done`。

几百个 case 的量级，整份重渲染就是几毫秒字符串拼接 + 一次 `write_text_file`，不值得为省这点开销去做增量。

### 4.4 输出位置

```
<workspace>/.apicase/reports/<YYYYMMDD-HHmmss>/report.html
```

- 放 `.apicase/` 隐藏目录——默认不出现在文件树，用例树保持干净；命名空间对齐 `.vscode/` / `.idea/` 的惯例，将来的缓存等内部数据也归它。**但隐藏不等于找不到**，见 4.5 的显示开关。
- `init_workspace` 时把 `.apicase/` 写进工作空间 `.gitignore`（无 `.gitignore` 则创建，已有则追加且去重）。
- 时间戳目录保留历史，为将来的趋势对比留位置。**不写 `latest.html`**——两份内容相同的文件会让用户搞不清该发哪个。

### 4.5 查看历史报告：两条通用能力，而非一个专用面板

历史报告的查看，由两项**各自独立成立的通用能力**组合而成——都不只服务本需求，复用价值高于再造一个专用列表面板：

**① 文件树「显示隐藏文件」开关**（默认关）

- `list_dir` 增参 `showHidden: bool`（缺省 `false`，保持现有行为），前端在工作空间维度持有开关状态。
- 入口放文件树**工具栏「⋯」或根行菜单**里的一个勾选项，对齐 VSCode / Finder 的惯例。开关翻转后清空子项缓存重新拉取。
- 隐藏项以**淡一档的文字色**渲染（同 VSCode 对 gitignored 文件的处理），一眼可辨"这不是普通用例"。
- 状态存 `sessionStorage` 还是 `settings.json`？——**`settings.json`**（跨启动的长期偏好，同主题/代理；不像面板显隐那样是会话级）。
- 这项能力本身就是缺的：用户的 `.env`、`.gitignore`、`.gitlab-ci.yml` 现在都看不到，跟报告无关也该有。

**② HTML 报告在 apicase 内可视化打开**

点 `report.html` 时：`read_file_smart` 取文本 → `parseReportHtml(text)` 尝试提取内联 JSON——

- **提取成功** → 开 `apicase://run/<路径哈希>` 标签页，`RunReportPane` 只读态（iframe + 无进度条的工具栏，见 4.3），与刚跑完时看到的界面完全一致。
- **提取失败**（普通 HTML）→ 现有纯文本视图，行为不变。

**apicase 只认自己生成的报告，不做通用 HTML 渲染器**——任意 HTML 直接塞进 iframe 既无产品价值，又等于在应用里跑一份来源不明的页面。先解析成 `RunReport`、再用自己的空壳渲染，等于隐含地做了一次格式校验：**能解析出结构化数据的才当报告，其余一律纯文本**。

**③「运行历史」列表面板降级为后续**

两项能力齐备后，历史查看的路径已经通了：开显示隐藏 → 展开 `.apicase/reports/` → 点某次的 `report.html`。**代价是时间戳目录名不携带信息**（看不出跑了哪个目录、通过率多少），要挨个点开才知道——所以一个带"时间 · 目标 · 环境 · 43/45 · 耗时"的列表仍有价值，但它是**锦上添花的专用 UI**，等报告真攒多了再做，那时也更清楚需要什么排序与筛选。本期先把通用机制做扎实。

**④ 设置页「通用 → 位置」增加"运行报告目录"一行**：`revealItemInDir` 定位到文件系统（Finder 对隐藏目录内的具体文件仍能正常展示）。那页本来就是"哪些数据存在哪"，报告目录属于这个集合。

### 4.6 后端：一个新命令 + 一处扩参

**新增 `ensure_dir`**——报告写盘复用 `write_text_file`，但现有命令覆盖不到报告目录的创建：

- `create_dir`（`lib.rs:518`）用的是 `fs::create_dir`（**单级**）且**已存在即报错**——而 `.apicase/reports/<时间戳>/` 是三级，且周期覆写时目录已存在是常态。它服务的是"新建文件夹"这个 UI 动作，"已存在即拒绝"对它是正确语义，不该为报告改它。
- `write_text_file` 用 `fs::write`，父目录不存在直接失败。

```rust
/// Tauri 命令：确保目录存在（多级创建，已存在不报错；报告输出目录用）。
#[tauri::command]
fn ensure_dir(path: String) -> Result<(), String> {
    std::fs::create_dir_all(&path).map_err(|e| format!("创建目录失败: {e}"))
}
```

**`list_dir` 增参 `show_hidden: Option<bool>`**（缺省 `false`，现有调用不受影响）——跳过 `.` 开头项的逻辑改为受此开关控制。`DirEntry` 顺带增一个 `hidden: bool` 字段，供前端做淡色渲染。排序规则不变（目录在前、组内按名忽略大小写）。

`.gitignore` 的写入走 `read_text_file` + `write_text_file`，报告读回走 `read_file_smart`，删除报告走 `delete_path`——**均为现有命令**。

### 4.7 为什么本期不下沉 Rust

后端目前完全不理解 case 结构——YAML 解析、`{{}}` 变量替换、JSONPath 提取、断言评估全在前端（`case.ts` / `flow.ts` / `draft.ts` / `auth.ts`）。下沉等于把这四个模块重写一遍 Rust，工作量比本需求本身还大，且要维护两套语义直到收敛。

**前端做，复用现有全部能力，一致性最好。** 等 `RunReport` schema 跑稳、真要做接 CI 的 `apicase run` CLI 时再下沉——那时契约已经现成，是自然的下一步。这条演进路径要写明，因为它决定了本期的数据模型必须"CLI-ready"（不含任何 React / DOM 概念）。

## 六、风险与边界

- **报告泄露凭据**：最高风险项。脱敏默认开启，且要有单测覆盖各类头名的匹配。UI 上不提供关闭入口（本期），避免误操作。
- **单文件体积**：64 KB/响应 × 几百个 case 仍可能到几十 MB。若实测超标，退路是"默认只保留失败用例的响应体，通过的只留状态码与耗时"——通过的用例本来就没人看响应内容。**体积对 apicase 内打开是双重成本**（读全文 + 正则切片 + `JSON.parse`），若成为瓶颈，退路是把 summary 单独内联成一小段前置 script，列表场景只读文件前若干 KB。
- **`parseReportHtml` 的脆弱性**：靠固定锚点 `<script id="apicase-report" type="application/json">` 切片，格式是自己生成的、可控，但**改 renderHtml 时必须同步 parse 侧**——`parseReportHtml(renderHtml(r))` 往返等价的单测就是防这个的护栏，必须有。用户手工编辑过报告导致提取失败时，静默降级为纯文本视图，不报错。
- **iframe 内的渲染逻辑无法用常规单测覆盖**：`REPORT_SHELL` 里的 JS 以字符串形式存在，`npm test` 那套 node 断言跑不到它。护栏只能是——渲染逻辑保持纯粹（`(RunReport) → DOM`，无网络无存储）、可测的部分（数据整形、筛选、脱敏展示）抽成模块级纯函数由 `renderHtml` 与 shell 共同引用，DOM 部分靠人工验收。若将来这块长大，值得引入一个轻量的 DOM 测试环境。
- **postMessage 的信任边界**：`srcdoc` 的 origin 是 `null`，收发都得用 `'*'`，故**宿主侧必须按 `type` 白名单处理并校验载荷**——`open-case` 带来的 `file` 要确认在当前工作空间之内（复用 `isUnder`），否则等于给了报告页任意打开本地文件的能力。iframe 保持 `sandbox="allow-scripts"`、**不给 `allow-same-origin`**（给了就等于放弃隔离）。
- **增量更新的正确性**：iframe 内按 case `file` 作 key diff。同一次运行里 `file` 唯一，可作稳定 key；但若将来支持"同一 case 重试多次"，key 要扩成 `file + attempt`，否则重试结果会覆盖首次结果。此处先记一笔。
- **`schemaVersion` 的用处在读回时兑现**：老版本 apicase 生成的报告被新版本打开，靠它决定能否解析 / 要不要做字段迁移。目前恒为 1，但读回逻辑要预留分支，不能假设永远匹配。
- **显示隐藏文件的副作用**：开启后 `.git/` 也会出现在树里，展开是几千个对象文件。`list_dir` 的 `show_hidden` 应**仍然硬跳过 `.git`**（以及既有的 `node_modules` / `target` / `dist` 约定），"显示隐藏文件"不等于"显示一切"。
- **`file://` 限制**：报告内不得有任何外部资源引用（字体、图标、CDN），全部内联或用系统字体栈 / 内联 SVG。
- **取消的语义**：只在 case 边界生效，已发出的 HTTP 不中断。长超时的请求会让取消看起来"没反应"——UI 上取消后状态应立即转「正在停止…」而非假装已停。
- **并发留位不留坑**：本期恒串行，但 `auth.ts` 的 OAuth2 token 缓存是模块级的，将来开并发时多个 case 会同时去换 token（不会出错，但会多打几次 token 接口）——届时需加 in-flight 去重，此处先记一笔。
- **外部文件变更**：批量运行期间用户若编辑了用例文件，运行的是**开跑那一刻读到的内容**（`runCase` 接收文本而非路径的原因之一）。报告里记的是文件路径，不记内容哈希——本期不做，但若将来要"报告可复现"，哈希是要补的字段。
- **报告目录膨胀**：每次运行留一份，长期会堆积。本期不做清理策略，但目录结构（时间戳一级目录）已使手动清理与将来的"仅保留最近 N 次"都好实现。
