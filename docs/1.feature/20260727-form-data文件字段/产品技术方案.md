# form-data：文件字段（multipart 上传）

_创建：2026-07-27_

## 需求

`20260723-请求体平铺与二进制` 把 form-data 从「假功能」做成了真发送，但**只有文本字段**——
`FormField` 仅 `name/value`，后端一律 `form.text(...)`。文件上传接口（`file=@xxx` 这类）
目前发不出去，只能退而用 `binary`（整个请求体一个文件、无字段名），语义不对。

本次补齐 form-data 的 **file 类型字段**：一行表单项可选「文本 / 文件」，选文件后
挑一个本地文件，发送时作为 multipart 的一个 part（带 filename 与该 part 的 Content-Type）。

## 方案

### 一、行内类型，而非新表

form-data 与 form-urlencoded 共用一张 `KVTable`（同一份 `ReqDraft.bodyForm`）。
**不为 form-data 单开一张表**——两者的行结构（启用 / 名称 / 值 / 描述）完全相同，
差别只在「值可以是文件」这一点。做法是给 KVTable 加一个 `withType` 开关（仅 form-data 传），
多出一列窄「类型」下拉（文本 / 文件），复用断言表已有的「单元格内嵌 `Select`」样式。

选「文件」后，该行的**值单元格**由输入框换成文件选择（「选择文件…」按钮 + 路径 + 垃圾桶清除），
路径展示沿用 binary 那套 `direction: rtl` 截前保后。行为对齐 Postman：
类型是**逐行**的，不是整表的；一张表里文本行与文件行可以混排。

**单文件**（Postman 支持一行选多文件）——多文件要引入「值是数组」的模型分叉，
而同名多 part 完全可以再加一行同名字段表达，收益不抵复杂度。

### 二、数据模型：复用 KV 行，加 `type: file`

`case.ts` 新增 `FormItem extends KV`，只多一个可选 `type`：

```ts
export interface FormItem extends KV {
  type?: "text" | "file"; // 默认 text（不落盘）；file 时 value 承载本地文件路径
}
```

**文件路径存进 `value`，不另立 `filePath` 子键**。理由：行结构保持统一，
`enabled` 禁用、`description` 备注、flow 的 `{{变量}}` 替换（`resolveKV` 只认 name/value）
全部天然复用；YAML 里 `type: file` 一眼可辨。对齐 Postman collection 的
`{key, type: "file", src}` 形态，只是把 `src` 并回 `value`。

YAML：

```yaml
body:
  type: form-data
  formData:
    - name: title
      value: 头像
    - name: file
      type: file
      value: ./avatar.png # 相对/绝对路径均可，支持 {{var}}
```

`type: text` 是默认值，不落盘（同 `enabled: true` 的裁剪规则）。

### 三、发送：文件名与 part 的 Content-Type 在前端算

`ApiRequestPayload.formData` 的元素由 `{name, value}` 扩为：

```ts
{ name, value?, filePath?, fileName?, contentType? }
```

有 `filePath` 即文件字段。**`fileName` 与 `contentType` 由前端算好一并传下去**：
前者取路径 basename（兼容 `/` 与 `\`），后者复用 binary 已有的 `guessContentType(path)`
（按扩展名，兜底 `application/octet-stream`）。这样后端不必再维护第二份 MIME 表，
「所见即所发」的推断逻辑也只有一处。

前端过滤规则：名称为空、或 `enabled === false` 的行跳过（同现状）；
**文件行路径为空**也跳过——空路径的 part 发出去只会让后端报读盘失败。

### 四、后端：`Part::bytes` + filename + mime

`FormField` 增三个可选字段（`file_path` / `file_name` / `content_type`）。
组装时按有无 `file_path` 分流：

```rust
if let Some(path) = &f.file_path {
    let bytes = std::fs::read(path).map_err(|e| format!("读取表单文件失败（{name} → {path}）: {e}"))?;
    let mut part = reqwest::multipart::Part::bytes(bytes).file_name(file_name);
    if let Some(ct) = &f.content_type { part = part.mime_str(ct).map_err(...)?; }
    form = form.part(name, part);
} else {
    form = form.text(name, f.value.clone());
}
```

错误信息带上**字段名 + 路径**——多文件表单里只报路径不容易定位是哪一行。
`file_name` 缺省时后端兜底取 basename（前端总会传，兜底是防御）。
读盘仍在后端（不把字节塞进 IPC），与 binary 一致。

### 五、multipart 判定放宽

现状「有无 form-data」的判据是「存在 name 非空的字段」。文件字段同样只按 name 判，
无需改判据；但**空表单不再退化**这点保持不变（无有效字段 → 不发 multipart，继续走
body_file / body 分支）。

## 落地文件

- `app/src/case.ts`：新增 `FormItem`；`BodySpec.formData` 改 `FormItem[]`；
  `normalizeFormData` / `serializeFormData`（在 KV 基础上带 `type`，`text` 不落盘）。

  `baseName()` 工具；`buildApiRequest` 组装 file 字段（filePath/fileName/contentType）。
- `app/src/flow.ts`：`resolveKV` 泛型化，保留 `type` 字段（文件路径中的 `{{var}}` 随 value 一并替换）。
- `app/src-tauri/src/lib.rs`：`FormField` 增 `file_path` / `file_name` / `content_type`；
  `perform_request` 的 multipart 分支按类型组 `Part`；新增离线测试

  form-data 传 `withType`。
- `app/src/App.css`：`.type-col` 列宽与内嵌下拉、`.cell-file`（单元格内文件选择）样式。
- `app/test/body.test.mjs`：补文件字段的载荷组装、跳过规则、YAML 往返用例。
