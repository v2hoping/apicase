# 节点失败传播：上游挂了，下游跳过

_创建：2026-08-02_

## 需求

### 现状：模型是 DAG，执行语义却是平铺列表

case 的模型是 DAG（step 之间用 `dependsOn` 声明依赖），但 `run_case` 目前是
**按拓扑序逐个跑完、失败也不管**：某个 step 挂了，下游照常执行。

这在真实用例里会产生两种坏结果：

```
uploadReport   error    ⚠ 读取请求体文件失败（./reports/月度报表.pdf）
afterError     passed   断言 3/3        ← 上游挂了，下游报告「通过」
```

1. **误报**。上游 error 时 outputs 为空，下游引用 `${{steps.uploadReport.outputs.uploadId}}`
   拿到的是保留下来的字面量。这个请求照样发出去、照样可能"通过"——报告说 passed，
   而实际上链路早就断了。比漏报更危险。
2. **真实副作用**。apicase 发的是**真实 HTTP 写请求**，不是纯计算。登录节点挂了，
   下游拿着字面量 token 去调 `DELETE /orders/123`，这个请求会实打实打到被测服务上。
   CI 里对着预发环境跑，后果是实际的。

第二条是 apicase 比通用工作流引擎**更需要**跳过的地方——Airflow、GitHub Actions 的
下游任务大多是幂等计算，我们的是写操作。

### 调研：分界线是「有没有声明依赖」

| 工具 | 模型 | 上游失败后，下游 | 逃生舱 |
|---|---|---|---|
| Postman Runner / Newman | 有序列表 | 照常跑 | `--bail`、`setNextRequest(null)` |
| Bruno CLI | 有序列表 | 照常跑 | `--bail`、`bru.stopExecution()` |
| JMeter | 有序列表 | 照常跑（Continue 是默认） | 线程组级 5 选一 |
| Apifox 测试场景 | 有序步骤 | 步骤级三选一 | 忽略 / 跳下一循环 / 结束执行 |
| **TestNG `dependsOnMethods`** | 依赖图 | **标记 SKIPPED，不跑** | `alwaysRun=true` |
| **pytest-dependency** | 依赖图 | **skipped，不跑** | — |
| **GitHub Actions `needs`** | DAG | **skipped，不跑** | `if: always()`、`continue-on-error` |
| **Airflow** | DAG | **`upstream_failed`，不跑** | `trigger_rule` |
| **n8n** | DAG | **整个工作流停止** | On Error: Continue / 错误输出分支 |
| **Postman Flows** | DAG（数据流） | **Success 端口下游收不到数据，不跑** | 连 Fail 端口 |

规律很清楚：**不是「API 工具」和「别的工具」之分，而是「有没有声明依赖」之分**。
平铺列表默认继续（项之间独立，要的是完整报告）；声明了依赖就默认不跑下游
（上游的产出是下游的输入，输入不存在时跑下游没有意义）。

Postman 一家同时有两套模型、选了相反的默认值，是最直接的佐证。

两条最贴近我们的先例：

- **TestNG** 的 `dependsOnMethods` 跟我们的 `dependsOn` 几乎同名，默认硬依赖——
  上游失败，下游报 **SKIP 而非 FAIL**，报告里用第三种颜色，文档专门强调
  「skipped 不等于失败」。
- **pytest-dependency** 给的理由更直白：**避免用一堆「事先就知道跑不通」的失败把报告搞脏**。

### 决策

1. **统一为跳过**：上游失败，下游不跑，标记为 `skipped`。
2. **error 恒阻断，不给选择**。请求根本没发出去，outputs 必然为空，下游产出 100% 是噪音。
3. **断言失败是否阻断，可配**：`settings.continueOnAssertionFailure`。
4. **配置是唯一默认源**，调试运行与批量运行都遵循它；**只有「运行并生成报告」可临时覆盖**，
   且**覆盖值记进报告**。

## 方案

### 一、状态模型：新增 step 级 `skipped`

`StepStatus` 加第五个值：

```rust
pub enum StepStatus { Passed, Failed, Error, Skipped, Running }
```

`StepResult` 加 `skip_reason: Option<String>`（形如 `上游 login 失败`），
与 `CaseResult.skip_reason` 同名同义——都回答"为什么没跑"。

**命名坑**：`CaseStatus::Skipped` 早就存在，但含义完全不同（文件读不到 / 不是有效用例 /
用例里没有请求）。两者在报告图例里会是两个灰格子写着同一个词。**靠 `skipReason` 区分**：
case 级写"读取失败：…"，step 级写"上游 X 失败"。不另造 `blocked` / `upstreamFailed`
这类新词——多一个状态词就多一套 CSS、筛选值和图例，而这两处的用户意图是同一个
（"这个东西没跑，原因在这儿"）。

`rollup` 里 **skipped 不改变 case 状态**：case 该是 error 还是 error，由根因节点决定。
一条链挂在第 2 步，case 的状态应该指向第 2 步，而不是被后面 8 个跳过的节点稀释。

### 二、传播规则

```
一个 step 被跳过 ⟺ 它的 dependsOn 传递闭包里，存在一个「阻断性失败」的 step
```

「阻断性失败」的判定：

| 上游状态 | 是否阻断 |
|---|---|
| `error` | **恒阻断**，不受配置影响 |
| `failed` | 阻断；`continueOnAssertionFailure: true` 时不阻断 |
| `skipped` | **阻断**（传递性：被跳过的节点没有产出，等同于没跑） |
| `passed` | 不阻断 |

两个要点：

- **按依赖闭包算，不按线性顺序**。DAG 里两条独立分支，一条挂了不该连累另一条——
  这正是 DAG 比线性列表值钱的地方。现有的 `stop_on_failure` 是在拓扑序遍历里直接
  `break`，会把毫不相干的分支一起砍掉，那个行为本身也是错的（本次不改它的语义，
  但新逻辑不沿用这个做法）。
- **skipped 要传递**。否则一条长链上，第 2 步挂了、第 3 步跳过、第 4 步又跑起来了。

### 三、三个开关的正交关系

这三件事容易被后人"统一"掉，写清楚各自管什么：

| 开关 | 管什么 | 暴露在哪 |
|---|---|---|
| **跳过传播** | 上游失败时下游跳过 | 不是开关，是默认行为 |
| **`continueOnAssertionFailure`** | 断言失败**算不算**阻断性失败 | 工作空间配置 + 报告运行面板 |
| **`stopOnFailure`** | 整轮运行立刻停（smoke test） | 仅报告运行面板 |

`stopOnFailure` 的语义**不变**（一个 case 非 passed 就停掉整轮），它和跳过传播正交：
前者管"要不要继续跑后面的 case"，后者管"case 内部谁该跑"。

### 四、配置

`application.yml` 的 `settings` 加一项，与 `verifySsl` / `timeoutMs` 并列：

```yaml
settings:
  continueOnAssertionFailure: true   # 断言失败不阻断下游；默认 false，写默认值不落盘
```

**命名为什么是 continue 而不是 ignore**：断言失败照样标红、照样计入统计、照样让 case 判
failed，变的**只是要不要挡住下游**。用 `ignore` 会让人以为失败被吞了。

**默认 `false`（阻断）**。这条配置随 git 传播给团队，团队约定该按 CI/回归的正确性定，
而不是跟着某个人的调试习惯走（同 `verifySsl`）。代价是开发期断言写错时下游会被挡住——
这个由「跳过的节点仍可单独发送」兜住（见下）。

解析沿用 settings 既有的兜底风格：**仅显式 `true` 才启用**，键缺失或类型写错都按 `false`。

### 五、调试运行与批量运行的一致性

批量运行在 Rust 里跑完整个 case（`run_case`），调试运行的循环在**前端**
（`onRunAll` 逐个调 `run_step`，为的是每跑完一步就刷新界面）。

**判定逻辑只写一份**：core 导出纯函数，前端经 IPC 调用，不在 TS 里重写一遍。

```rust
/// 给定 steps 与「已阻断」的 step id 集合，算出还有哪些 step 该被跳过。
pub fn blocked_steps(steps: &[Step], blocking: &[String]) -> Vec<String>
```

前端每跑完一个 step，若它是阻断性失败就把 id 加进集合，调一次拿到要跳过的 id，
后续循环里遇到就标 skipped 直接跳。这与 `topo_order` 的处理方式一致——
**排序规则、传播规则这类边界只在 Rust 有一份实现**。

### 六、UI

**「仍然运行此节点」不新做**：每个节点本来就有「发送」按钮，跳过的节点照样能点，
走的是 `onSendRequest`（用当前 outputs 上下文）。调试是探索性的——用户往往是看到
"哦上游挂在这儿"之后才知道想不想看下游，**运行前的选择框问的是一个此刻还答不上来的问题**。
所以调试运行**不引入任何运行前配置**：默认跟配置走，剩下的靠单独发送兜住。

- **节点跳过态**：灰色 + 提示"上游 X 失败，已跳过"。
- **设置 → 通用**：加开关，与 SSL / 超时同组。
- **运行并生成报告对话框**：加复选框，初值取配置，**改了不回写 `application.yml`**
  （跑一次报告就悄悄改了团队配置，是很难查的坑）。

### 七、报告

`RunOptions` 加 `continue_on_assertion_failure`，与 `stop_on_failure` / `redact` 并列。

**HTML 报告头部要显示本次策略**，不能只记进 JSON。否则人看报告时，面对一堆灰色的
跳过节点，答不出"这次是什么策略"，也就判断不了"这些节点为什么没跑"；两份结论不同的
报告摆在一起，也分不清是服务变了还是选项变了。

**`REPORT_SCHEMA_VERSION` 1 → 2**。注意版本号是为 `StepStatus::Skipped` 动的，
不是为新增字段动的：加字段对旧解析器向后兼容，而**新增一个状态枚举值不兼容**——
旧报告页遇到没见过的状态，不知道该渲染成什么颜色、该不该计入统计。

### 验证用例

`~/development/local/apitest/08-失败与下游/` 已有两条流程，正好是这次的回归基线：

| 用例 | 改动前 | 改动后（默认配置） |
|---|---|---|
| `断言失败-下游照常执行.yml` | 3 个节点全跑，case failed | 第 3 步 **skipped**，case 仍 failed |
| `请求错误-下游变量丢失.yml` | 3 个节点全跑，case error | 第 3 步 **skipped**，case 仍 error |

开 `continueOnAssertionFailure: true` 后，第一条恢复成 3 个节点全跑（error 那条不变）——
这一对正反用例就是开关生效的证据。用例文件名与 README 的预期表需要同步更新。
