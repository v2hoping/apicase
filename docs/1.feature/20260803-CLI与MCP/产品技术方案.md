# apicase CLI 与 MCP

_创建：2026-08-03_

## 需求

1. **CLI 能完成全部操作**。`apicase run /path/to/case.yml` 这类形式直接运行；编辑与改配置因为
   本就是 YAML 文本，直接编辑文件即可，CLI 不必再造一套编辑命令。
2. **支持 MCP**，让 AI Agent 配一条 MCP 命令即可操作 apicase。
3. **命令简化通用，人与 AI Agent 都好用**。
4. **与界面同属一个客户端**：点图标或敲界面命令，能开界面就开；开不了（如没装桌面环境的
   Linux）要**说清原因**而不是无声失败。
5. **遵循业界规范**：正式、标准、简洁、清晰。

## 现状：内核早已就绪，缺的是外壳

执行语义在 2026-07-30 那次改造中已整体下沉到 `apicase-core`（零 Tauri / 零 GUI 依赖），
`core/examples/run_workspace.rs` 就是**无界面跑完一个工作空间**的可行性验证：
读配置 → 发现用例 → 执行 → 落一份与桌面端逐字相同的 HTML 报告 → 按结果返回退出码。
`app/Cargo.toml` 的注释里也写明了「将来的 `cli/` 作为第三个成员加进来即可」。

所以本期做的**不是**「再写一个执行器」，而是给已有内核补三层外壳：
命令行界面与 MCP 协议界面。

## 决策一：双二进制，而不是一个二进制两种模式

「同一个客户端」有两种实现方式：

| | A. 单二进制多模式 | B. 双二进制（选此） |
|---|---|---|
| 形态 | `apicase` 里既有 Tauri 又有 CLI，按 argv 分流 | `apicase`（CLI+MCP）与 `Apicase`（桌面）各一个 |
| 无桌面环境的 Linux | **`apicase run` 直接起不来** | CLI 完全可用 |
| macOS | 裸二进制跑 Tauri 行为异常（NSApplication 需要 bundle） | 桌面走 .app，CLI 走裸二进制 |
| CLI 体积 / 冷启动 | 拖上整个 WebView 框架 | 只有内核 |
| 单独分发 CLI（CI 容器、`cargo install`） | 做不到 | 天然可以 |

**A 的第一条是致命的**：Linux 上 Tauri 动态链接 `libwebkit2gtk-4.1.so`，没装 webkit 的
机器上动态链接器在 `main` 之前就会失败——连"提示原因"的机会都没有，用户看到的是
`error while loading shared libraries`。而需求 4 恰恰要求这种环境下"说清原因"。

选 B。这也是业界主流形态：VSCode 的 `code`、Docker Desktop 的 `docker`、JetBrains 的
`idea` 都是独立于 GUI 进程的入口。

**"同一个客户端"靠三件事成立**，而不是靠共用一个进程：

1. **同一个执行内核**。CLI 与桌面壳平行依赖 `apicase-core`，不存在"界面里跑过了、CLI 跑却挂了"。
   这一点是 Newman 相对 Postman 做不到的（两套实现），也是 apicase 的既有优势。
2. **同一份数据**。工作空间 `application.yml`、cookie jar `.apicase/cookies.json`、
   报告目录 `.apicase/reports/` 三者共享。CLI 跑出的报告在界面的文件树里点开就能看，
   CLI 登录留下的会话界面里接着用。
3. ~~**互相唤起**~~。原计划 `apicase gui` 唤起界面 + 桌面端「安装命令行工具」，
   前者已于 2026-08-04 取消（见下方「变更」一节），后者属分发环节、待做。

分发上，CLI 二进制经 Tauri 的 `bundle.externalBin` 打进安装包，与桌面二进制同处一个 bundle。

> **一个必须避开的坑**：macOS 与 Windows 的文件系统**默认大小写不敏感**，而 Tauri 在 macOS 上
> 用 `productName` 作 bundle 内的可执行名（`Apicase`）。CLI 若也叫 `apicase` 放在同一目录，
> 两者是同一个文件名——不仅装不进去，`apicase gui` 找桌面端时 `dir.join("Apicase").is_file()`
> 还会命中 CLI 自己，结果是反复启动自身。
> 因此 **bundle 内的 CLI 命名为 `apicase-cli`**，PATH 里的软链才叫 `apicase`；
> 并且查找逻辑按**规范化后的真实路径**排除自身（有测试钉住）。

## 决策二：CLI 与 MCP 共用一层「操作层」

需求 3 说「人和 AI Agent 均使用方便」。若 CLI 与 MCP 各写一遍业务，两者必然漂移——
这正是 core 下沉时要消灭的那类技术债，不该在上层重新长出来。

```
              apicase-core        执行语义（已有）
                    ↑
              cli/src/ops.rs      操作层：run / list / check / show / env / report / cookie
                    ↑             —— 与呈现无关、与协议无关，返回结构化 Rust 类型，零 stdout 输出
            ┌───────┴───────┐
      cli/src/cmd/*      cli/src/mcp.rs
      文本与 JSON 渲染      MCP 工具定义
```

**操作层的硬约束是「不 print」**。它返回数据，怎么显示由外壳决定。这条不只是洁癖：
MCP 的 stdio 传输规定 **stdout 只能有协议消息**，操作层里漏一行 `println!` 就会破坏
JSON-RPC 帧，表现为 MCP 客户端"连上了但什么都不工作"，且极难定位。

由此，每个 CLI 子命令与每个 MCP 工具都只是同一个 ops 函数的两种外壳，参数名与语义
一一对应——AI 读过 `apicase run --help` 就会用 `apicase_run` 工具，反之亦然。

## 决策三：MCP 协议层用官方 SDK，不手写

本项目在很多地方选择手写而非引库（YAML 输出器、JSONPath、HTTP 测试服务、日历排布）。
MCP 这里**反过来**，理由是这两类东西的性质不同：

- **YAML 输出格式是产品面**。落盘的 case 是用户要读、要 diff、要 review 的源文件，
  引号加在哪里是产品决策，必须自己掌控。
- **MCP 是协议帧**，产品面为零。它唯一的价值是"能被各家客户端连上"，而这恰恰是最不该
  自己承担的部分。

且协议正在快速演进：`2025-06-18` → `2025-11-25` → `2026-07-28`，一年三版，最后一版是
**破坏性的无状态改造**——移除了 `initialize` / `notifications/initialized` 握手，改为每个请求
在 `_meta` 里携带协议版本，并新增 `server/discover`。现实中的客户端跨越这两个时代，
服务端要同时应付：现代客户端先 `server/discover` 探测，旧客户端直接 `initialize`，
且**回退不能只认某一个错误码**（规范明确要求）。这张兼容矩阵是 SDK 的职责，不是我们的领域知识。

用官方 Rust SDK [`rmcp`](https://crates.io/crates/rmcp)（3.x，实现 2026-07-28 并向后兼容旧版）。

**风险对冲**：MCP 层收敛在 `cli/src/mcp.rs` 一个文件里，只做「工具定义 + 参数解包 + 调 ops +
把结果转成 `CallToolResult`」。业务零行。SDK 若有破坏性变更或需要换实现，受影响的是这一个文件。

## 决策四：先往 core 下沉三块公共能力

CLI 要用、桌面端已经在用（但实现散在别处）的三块：

| 下沉项 | 现在在哪 | 问题 |
|---|---|---|
| **工作空间**：定位、读 `application.yml`、组装 `RunOpts` / `ClientConfig` | `examples/run_workspace.rs` 的一段胶水 | 是示例代码，不是可复用 API |
| **用例发现**：递归、排除规则、排序 | 示例里一份 + 前端 `discoverCases` 一份 | 已经两份了，CLI 会变第三份 |
| **报告文件命名 + 周期写盘** | 文件名在前端 `reportFileName`，写盘在 `src-tauri` 的 `ReportWriter` | CLI 要复刻两份 |

新增 `core/src/workspace.rs` 与 `core/src/discover.rs`，并把 `ReportWriter` 移入 core。
桌面壳改为引用同一份（`ReportWriter` 连同它的既有测试一起搬）。

这是本期对 core 唯一的实质增量，且方向与既有架构一致：**凡是 CLI 与桌面端都要做的事，
就该在 core 里只有一份**。

## 命令规范

### 总览

```
apicase <命令> [选项]

  run          运行用例或目录
  ls           列出用例
  check        校验用例（不发请求）
  show         查看用例详情
  new          新建用例
  env          环境：list / show
  cookie       Cookie：ls / rm / clear
  report       报告：ls / show / open
  init         把目录初始化为工作空间
  docs         查看用例 YAML 的格式规范
  mcp          以 MCP 服务器运行（stdio）
  completion   生成 shell 补全脚本

全局选项：
  -w, --workspace <目录>   工作空间根（默认：从目标或当前目录向上找 application.yml）
  -e, --env <名称>         环境名
      --format <text|json> 输出格式（默认：终端下 text，管道下 json）
      --json               = --format json
      --color <auto|always|never>
  -q, --quiet              只输出结果，不输出进度
  -h, --help / -V, --version
```

`docs` 是实施时加的：**人和 AI 查的应该是同一份规范**，不该有「文档」和「给 AI 的文档」两种说法。
它与 MCP 的 `apicase_docs` 共用 `docs.rs` 那一份分节逻辑。

原计划的 `-v/--verbose` 去掉了：`run` 的文本输出本就带失败现场、JSON 有 `--detail full`，
再加一档「更详细」既没有明确的内容，也会与 `--detail` 语义重叠。

**无参数时打印帮助，而不是开界面**。这是 CLI 的通例（git / docker / cargo），且在终端敲
`apicase` 时弹出一个窗口是一种惊吓。

### `apicase run`

```
apicase run [选项] [目标]...

  目标   用例文件 / 目录 / `-`（从 stdin 读一份用例）。省略 = 整个工作空间

      --step <ID>       只跑指定 step（可重复，自动带上它的依赖）
  -j, --concurrency <N> case 之间的并发（默认 1）
      --bail            首个失败即停
      --continue-on-assertion-failure   断言失败不阻断下游 step
      --var <K=V>       追加 / 覆盖环境变量（可重复）
      --timeout <毫秒>   覆盖工作空间的超时设置
      --insecure        跳过 TLS 证书校验
      --no-recursive    目录不递归
      --report <文件>    HTML 报告落盘路径
      --no-report       不落盘报告
      --detail <summary|full>   JSON 输出的详略（默认 summary）
```

几处刻意的设计：

- **目标可以是任意路径**，工作空间从目标所在目录**向上找 `application.yml`**（同 git 找 `.git`）。
  于是 `apicase run /other/project/api/login.yml` 自动用那个项目的环境与设置，
  在子目录里敲 `apicase run` 也照常工作。找不到就退出并提示 `apicase init`。
- **`--var` 是往活动环境里追加**，仍会被 case 级 `vars` 覆盖。语义与「环境变量」一致，
  可解释，且执行内核一行不改（只改 `EnvironmentInfo.vars`）。CI 注入密钥、AI 传参都走这里。
- **`-` 从 stdin 读一份用例**：AI 生成一段 YAML 直接跑，不必先落盘。报告里 `file` 记为 `<stdin>`。
- **`--step` 自动带上依赖**：只写要跑的那个，上游由 core 的依赖闭包补齐——
  否则用户得自己把整条链列出来，而链是 DAG 里最容易列错的东西。

### 输出

**text（给人看）**，进度逐行打印、不用会被 CI 日志打乱的原地刷新：

```
工作空间  demo (/Users/me/demo)        环境  dev
用例  12 个

  ✓ api/health.yml                      42ms
  ✕ api/login.yml                       318ms   断言 1/2
      res.body.data.token   exists   →  ∅
  ! api/order.yml                          —    连接被拒绝 (127.0.0.1:8080)
  – api/report.yml                         —    上游 login 失败

用例  12   通过 10   失败 1   错误 1
请求  28   通过 25   失败 1   错误 1   跳过 1
断言  54   通过 52   失败 2
耗时  3.2s
报告  .apicase/reports/20260803143022-api.html
```

用例行与请求行分开，沿用 `run_workspace` 已有的决策：用例级的「跳过」是这个文件没跑，
请求级的是上游挂了没轮到它，合并计数会让排查时分不清。

**json（给机器看）**：直接输出 `RunReport`。它已经是执行与渲染之间的既有契约，
带 `schemaVersion`，与 HTML 报告内联的那份 JSON 完全相同——**一套数据契约，三处消费**
（报告页 / CLI / MCP）。`--detail summary`（默认）裁掉报文体与通过项的明细，
只留统计与失败现场；`--detail full` 给完整报告。

裁剪是必须的：一份 500 用例的完整报告有几 MB，无论是灌进 AI 的上下文还是管道给 `jq`，
默认给全份都是错的默认值。

**格式默认值跟着 TTY 走**：终端里是 text，`apicase run | jq` 时自动 json。
颜色遵守 [`NO_COLOR`](https://no-color.org/) 与 `--color`。

### 退出码

| 码 | 含义 |
|---|---|
| `0` | 全部通过 |
| `1` | 有断言失败（`failed`）——**被测服务**的问题 |
| `2` | 用法 / 配置错误（参数非法、找不到工作空间、目标不存在）——**工具层面** |
| `3` | 有执行错误（`error`，或用例级 `skipped`）——**环境或用例自身**的问题 |
| `130` | 被 Ctrl-C 中断 |

1 与 3 同时出现取 3（跑都没跑起来比断言没过更严重）。

`2` 留给用法错误是 GNU 工具的强约定（`grep`：0 匹配 / 1 不匹配 / 2 出错；`diff` 同）。
`1` 与 `3` 的区分则是 apicase 特有的：**`failed ≠ error` 是内核的核心理念**
（写在 `report.rs` 的类型注释里），退出码若不体现它，等于在 CI 那一层把最有用的信息丢掉了。
参照 Hurl 也把「运行时错误」（3）与「断言失败」（4）分开；Newman / Bruno 则一律 1。

### 其余命令

| 命令 | 说明 |
|---|---|
| `apicase ls [路径]` | 列用例：路径、名称、step 数、方法与 URL 概要。`--json` 给结构化清单 |
| `apicase check [目标]...` | 只解析不发请求，报出 YAML 语法错、缺 `steps`、旧 `http:` 键、依赖成环、`dependsOn` 指向不存在的 step。**给 AI 的自检入口** |
| `apicase show <用例>` | 看一个用例：`--format yaml` 给规范化原文，`--format json` 给结构化模型 |
| `apicase new <路径>` | 脚手架：`--method` / `--url` / `--name`，生成后打印路径 |
| `apicase env [list]` / `env show [名称]` | 列环境、看某套环境的变量 |
| `apicase cookie ls / rm / clear` | 复用 core 的 jar 管理接口，与设置页「Cookies」同一份实现 |
| `apicase report ls / show [文件] / open [文件]` | 列历史报告、读回结构化摘要（走 `parse_report_html`）、用系统默认程序打开 |
| `apicase init [目录]` | 写 `application.yml` 模板，幂等 |
| `apicase completion <bash\|zsh\|fish\|powershell>` | 补全脚本（clap_complete 生成） |

参数解析用 `clap` 4 的 derive API。这是 Rust 生态的事实标准，并且免费带来规范的 `--help`、
子命令、以及补全生成——手写这些很快会失控，而"遵循业界规范"正是需求里点名的一条。

## 变更（2026-08-04）：取消 `apicase gui`，两个二进制彻底独立

下面这一整节**已作废**，`cli/src/gui.rs` 连同它的四项测试一并删除。保留原文是为了记住
当时的推理，以及为什么后来判断它不值得。

改动后的形态是最简单的那种：

| 产物 | 来源 | 用途 | 依赖 |
|---|---|---|---|
| `apicase` | `cli/` | 命令行与 MCP | `apicase-core` |
| `apicase-desktop` | `src-tauri/` | 图形界面 | `apicase-core` + Tauri |

**互不引用**，唯一交集是共同依赖 `apicase-core`。要命令行就敲 `apicase`，要界面就开
`apicase-desktop`，各自 `cargo build` 出各自的可执行文件。

取消的理由：唤起那条链路要维护**一整套猜测逻辑**——桌面端装在哪（四处查找路径 ×
三个平台的常规位置）、这台机器能不能开图形界面（`DISPLAY` / `WAYLAND_DISPLAY`）、
三类失败各自怎么措辞。它还引出了两个真实的坑（大小写不敏感的文件系统上
`Apicase` 命中 CLI 自己；`APICASE_GUI` 在并行测试里互相抹掉）。
而这一切换来的，只是省掉用户点一下应用图标。

**「同一个客户端」这个诉求本来也不是靠唤起满足的**——它靠的是同一个执行内核与同一份数据
（工作空间配置、cookie 会话、报告目录），那两条一行没动。

保留的是**桌面端自己认启动参数**（`startup_workspace()`）：它读的是自己的 argv，
与 CLI 无关，支撑 `apicase-desktop <工作空间>` 与「把目录拖到应用图标上」，
是桌面端独立可用的能力，删掉只会白白少一个入口。

## ~~`apicase gui`：能开就开，开不了说清为什么~~（已作废）

```
apicase gui [工作空间路径]
```

三步，每一步的失败都有各自的说法：

**① 找桌面二进制** —— `APICASE_GUI` 环境变量 → 与 CLI 自身同目录（安装包内的 bundle 布局）
→ 平台常规位置（macOS `/Applications/Apicase.app`、Windows `%LOCALAPPDATA%\Programs\`、
Linux `/usr/bin/apicase-desktop` 与 `~/.local/bin`）→ PATH。都没有：

```
未找到 apicase 桌面端。
命令行功能不受影响；如需界面，请安装桌面版，或用 APICASE_GUI 指定可执行文件路径。
```

**② 检测显示环境**（仅 Linux / BSD 需要；macOS 与 Windows 恒认为有）——
`DISPLAY` 或 `WAYLAND_DISPLAY` 有其一即可。都没有：

```
当前环境没有图形显示服务（未检测到 DISPLAY / WAYLAND_DISPLAY）。
apicase 的界面需要桌面环境；命令行功能不受影响，可继续使用 apicase run。
```

两种失败**必须分开说**：一个是"没装"，一个是"装了但这台机器上开不出来"，
用户要做的事完全不同。合并成一句"无法打开界面"等于什么都没说。

**③ 启动**：以 detached 方式 spawn，立刻返回（不占住终端）。工作空间路径作为参数传入。

为此桌面壳要新增**接收启动参数**的能力：`Apicase <工作空间>` 启动时直接打开该工作空间。
实现是一条命令 `startup_workspace()` 返回 argv 里的路径，前端在启动时若拿到就直接打开——
顺带让"从文件管理器把工作空间拖到图标上"这类系统集成也有了着落。

反向的一环：桌面端设置页「通用」加**「安装命令行工具」**，把 bundle 内的 CLI 符号链接到
`/usr/local/bin/apicase`（同 VSCode）。装了桌面版的人因此白得一个 CLI，这是"同一个客户端"
在用户感知层面真正成立的地方。

## MCP 契约

启动：`apicase mcp`（stdio 传输）。客户端配置形如

```json
{ "mcpServers": { "apicase": { "command": "apicase", "args": ["mcp", "-w", "/path/to/workspace"] } } }
```

`-w` 省略时，工作空间按 MCP 客户端的工作目录向上找——与 CLI 同一套规则。

### 工具

七个，与 CLI 子命令一一对应。带 `apicase_` 前缀（同 Playwright MCP 的 `browser_*`），
避免多 server 并存时 `run` / `list` 这类通名撞车。

| 工具 | 参数 | 说明 |
|---|---|---|
| `apicase_run` | `target?` `content?` `env?` `steps?` `vars?` `concurrency?` `detail?` `report?` | 运行用例 / 目录 / 内联 YAML |
| `apicase_check` | `target?` `content?` | 校验，不发请求 |
| `apicase_list` | `path?` `query?` | 列用例 |
| `apicase_show` | `target` `format?` | 看一个用例 |
| `apicase_env` | `name?` | 列环境与变量 |
| `apicase_report` | `file?` `filter?` `detail?` | 读报告（默认最近一份） |
| `apicase_docs` | `topic?` | 返回 case YAML 格式规范 |

几处与 CLI 刻意不同的默认值，理由都是"调用方不是人"：

- **`apicase_run` 默认不落盘 HTML 报告**（CLI 默认落）。AI 调 run 多半是"验证我刚写的这个用例
  对不对"，每次调用甩一份几 MB 的 HTML 进工作空间是污染。要就传 `report: true`。
- **`detail` 默认 `summary`**，且比 CLI 的 summary 更紧：只给统计 + 失败的那几步的
  target / expected / actual。上下文是 AI 最稀缺的资源。
- **`apicase_docs` 是给 AI 的入口条件**。AI 不知道 apicase 的 YAML schema，靠猜必然写错。
  内容用 `include_str!` 直接嵌 `docs/0.latest/3.YAML格式规范.md` 并按二级标题分节
  （`topic` 选 `case` / `assertions` / `auth` / `body` / `vars` / `settings`），
  **不另写一份速查**——单一事实源，零同步成本。默认返回总览与 step 那几节。

配上 `apicase_docs` + `apicase_check`，AI 的闭环是：**查格式 → 用自带的文件工具写 YAML →
check 自检 → run 验证 → 读失败现场改**。写文件不做成工具，正是因为需求里说了
「编辑和改配置因为是 yml 文本，可以直接编辑文本完成」——AI 的文件工具已经够用，
再包一层只会多一道权限与语义的错位。

### 资源：本期不做

原计划暴露 `apicase://docs/case-format` 与 `apicase://workspace/application.yml` 两个 resource，
落地时去掉了：**`apicase_docs` 与 `apicase_env` 已经给出同样的内容**，而 resources 在各家客户端
的支持程度参差不齐（有的根本不读、有的要用户手动挂载）。同一份内容两条取用路径，
换来的只是「某些客户端里多一个可点的条目」，代价是多一套要维护的 URI 与订阅语义。
真有客户端只吃 resources 时再加不迟。

### stdout 纪律

MCP 模式下 **stdout 只能有 JSON-RPC 消息**，日志一律走 stderr（规范允许 stderr 写任意 UTF-8）。
操作层的"不 print"约束（决策二）就是为这条服务的。加一个测试：以 `mcp` 模式起进程、
发一轮握手与 `tools/list`，断言 stdout 的每一行都能解析成 JSON。

| **P2** | JUnit XML 报告（CI 集成）；`--watch`；MCP 的 Streamable HTTP 传输；MCP resources | 待做 |

P0 一次做完，`show` / `new` / `env` / `cookie` / `report` 这几个原计划放 P1 的子命令一并落地了——
它们都只是 ops 的一层薄壳，拆开做反而要多写一次接线。

**顺带退休了 `core/examples/run_workspace.rs`**：它的定位是「CLI 的可行性验证」，
使命已经完成，留着就是第二份「读工作空间 → 发现用例 → 跑 → 落报告」的实现。

**帮助文本一并中文化**：`help_template` 与分组标题经一层 `localize()` **递归传播到每个子命令**
（derive 的 `#[command(help_template)]` 只作用于它所在那一层，而 `apicase run --help`
比顶层帮助更常被读到）。取舍：`[OPTIONS]`、`Arguments:`、`[default: …]` 这些留英文——
前两个是占位符不是文案（各家 CLI 一律英文），最后一个是 clap 在 build 期硬编码的、derive 够不着。
内置的 `help` 子命令关掉（`disable_help_subcommand`），理由同上：它那行说明改不了，
而 `apicase run --help` 完全等价（ripgrep、fd 等现代 CLI 同样只留 `--help`）。

| `cli` 集成（9） | **把二进制真的跑起来**看退出码（0/1/2/3 各一条）、`--json` 的 stdout 是否干净、报告落点与 `.gitignore` |

集成测试单独一层，是因为退出码是 CLI 与 CI 之间**唯一的契约**，
而单测只能覆盖「算出来的码对不对」，覆盖不了「这个码有没有真的被返回」——
中间还隔着 `ExitCode::from`、`?` 的早退、panic。它起了个手写的极简 HTTP 服务
（30 行，只会回一句 200），因此不依赖网络。

### 风险

- **rmcp 3.x 发布不足一周**（3.0.0 与 2026-07-28 规范同日）。缓解：MCP 层收敛在一个文件；
  若 3.x 不稳可退回 2.2.0（对应 2025-11-25，覆盖当前绝大多数客户端）。
- **Linux 打包**：deb / AppImage 下 `externalBin` 的落点与 `/usr/bin` 的软链需要另行处理。
  不影响 P0——`cargo build -p apicase-cli` 出的二进制本身就是完整可用的。
- **core 新增文件系统访问**。`discover` / `workspace` 要读目录、向上遍历，边界（权限不足、
  符号链接成环、到达文件系统根）一律回落为"没找到"而不是报错或死循环，与 core 既有的
  容错风格一致。
