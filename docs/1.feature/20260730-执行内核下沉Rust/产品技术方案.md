# 执行内核下沉 Rust

> 把「从 case 文件到运行报告」的全部执行语义从前端下沉到一个独立的 Rust crate，
> 界面退回它该待的位置——**只做配置与展示**。同时为无界面的 `apicase run` CLI 铺好地基。

## 一、需求内容

### 1.1 现状：执行语义长在前端

改造前，一次请求从配置到结果，中间**每一步都在浏览器里**：

| 环节 | 改造前 | 文件 |
|---|---|---|
| case YAML 解析 | 前端 js-yaml | `case.ts` |
| 变量透传 `${{}}` | 前端 | `flow.ts` |
| 请求组装（认证头 / Content-Type / multipart） | 前端 | `draft.ts` |
| Digest 摘要、OAuth 2.0 换 token | 前端（自带 MD5 实现） | `auth.ts` `md5.ts` |
| JSONPath 提取、断言评估 | 前端 | `flow.ts` |
| 批量执行、脱敏、截断 | 前端 | `runner.ts` |
| 报告 HTML 渲染 | 前端 | `report.ts` |
| **实际发出 HTTP** | Rust `send_request` | `lib.rs` |

Rust 只剩最后一步——**一个纯粹的传输管道**，收到什么发什么。

这个划分有三个具体后果：

1. **CLI 无法复用**。`apicase run` 要能无界面跑用例、出报告，而这些能力全在 React 应用里。
   照现状做 CLI，等于把上表前七行**在 Rust 里重写一遍**——从此两套实现并行演进，
   「界面里跑过了、CLI 跑却挂了」只是时间问题。
2. **性能上限被锁死**。每发一个请求都 `Client::builder().build()` 一次：TLS 根证书库重建、
   连接池随客户端一起丢弃。批量跑 100 个打同一服务的用例，就是 100 次 TCP + 100 次 TLS 握手。
   而 case 之间的并发根本无从谈起——JS 单线程、`await` 串行，`concurrency` 参数位空放着。
3. **报文体在 IPC 上来回搬**。响应先由 Rust 读成 String、序列化过 IPC、在 JS 里再解析一次，
   然后脱敏、截断、渲染，最后把渲染好的 HTML 又送回 Rust 写盘。

### 1.2 目标

**界面只做两件事：把配置递下去，把结果画出来。**

```
┌─ 界面（React）────────────────────────────────┐
│  编辑 case · 编辑设置 · 画响应 · 画报告        │
└───────────────── invoke / event ──────────────┘
┌─ 桌面壳（Tauri）──────────────────────────────┐
│  命令转发 · 文件树 · fs 监听 · 伪终端          │
└───────────────────────────────────────────────┘
┌─ apicase-core（零 GUI 依赖）──────────────────┐
│  YAML → 变量 → 组装 → 认证 → 发送             │
│       → 提取 → 断言 → 脱敏 → 报告              │
└───────────────────────────────────────────────┘
                     ↑
            将来的 apicase run CLI
```

### 1.3 CLI 就绪（本期不做实现，但要能证明）

用户明确「之后会出 CLI 端，可以无界面执行各种操作」。本期**不做 CLI 本体**，
但要求架构对它就绪，且**能被验证**——不能只是嘴上说"以后接上就行"。

验证方式：`core/examples/run_workspace.rs`，一个不含任何 Tauri / React 的示例，
读工作空间 → 发现用例 → 执行 → 落报告 → 按结果返回退出码。它跑通了，CLI 就只剩参数解析。

## 二、架构：三层与两条边界

### 2.1 core 的边界：不依赖 Tauri

`apicase-core` 的 `Cargo.toml` 里**没有 tauri**。这条边界一旦破掉（比如为了发个进度事件
而 `use tauri::Emitter`），CLI 就得把整个 GUI 框架拖进来编译。

因此进度上报走**回调注入**（`ProgressFn`）而不是直接 emit，桌面壳在回调里转成 Tauri 事件，
CLI 在回调里打印一行。

### 2.2 桌面壳的边界：不含执行语义

`src-tauri` 从 1398 行的单文件拆成 6 个模块，其中 `commands/exec.rs` 是**纯转发**：
把 JSON 变成 core 的类型、把产物变回 JSON、把进度转成事件。任何漏进这一层的语义，
都是 CLI 将来要重写一遍的技术债。

| 模块 | 归属 | 为什么不在 core |
|---|---|---|
| `exec` | 转发 core | 只做类型转换与事件推送 |
| `fs` | 桌面壳 | 隐藏项过滤、二进制嗅探是为文件树服务的 |
| `watch` | 桌面壳 | 实时刷新文件树；CLI 是一次性执行 |
| `terminal` | 桌面壳 | 底部终端面板 |
| `app` | 桌面壳 | 应用配置目录由 Tauri 按 identifier 推导 |

### 2.3 前端留下什么

删掉 `flow.ts` / `runner.ts` / `report.ts` / `md5.ts`；`case.ts` 退化为类型定义 + IPC 封装，
`auth.ts` 只剩显示元信息，`draft.ts` 只剩编辑态 ↔ HttpSpec 互转。

**唯一刻意留在前端的执行相关逻辑**是 `splitQueryFromUrl` / `mergeQueryIntoUrl`：
它们在 URL 输入框的**打字热路径**上（每敲一个字符都要调），走 IPC 会让输入变黏手。
Rust 侧有等价实现服务于发送，两边各有单测钉住行为。

## 三、关键决策

### 3.1 YAML 解析：Rust 唯一实现

CLI 必须能自己读 case，所以 Rust 侧一定要有一份。问题只是前端是否还留一份。

**决定：Rust 唯一，前端 `parseCase` / `dumpCase` / `analyzeCase` 变异步 IPC。**

代价是 `App.tsx` 约 15 处调用要改成 `async`。收益是 schema 单点——加一个字段只改一处，
不存在漏改导致「界面能打开、CLI 读不了」的可能。

这些调用全在**用户操作边界**（打开文件、切视图、保存），一次 IPC 往返不到 1ms，感知不到。

### 3.2 YAML 引号与变量语法（本期一并解决）

改造前 js-yaml 生成的文件里有这样的行：

```yaml
      value: bar        # ← 不带引号
      value: '2'        # ← 带引号，同一列两副面孔
      x: 502
      'y': -70          # ← 连 key 都带上了
```

这里面其实混了**三个不同的问题**，前两轮各只解决了一部分，最后收敛成下面这套。

#### ① `'y': -70` —— YAML 1.1 的布尔别名

js-yaml 按 **YAML 1.1** 输出，1.1 把 `y` / `n` / `yes` / `no` / `on` / `off` 都当布尔别名，
于是给 key 加了引号。**1.2 取消了这些别名**，我们的解析器（`serde_yaml`）也按 1.2 读。
故 key 位置只需"读得回原值就裸写" → `y: -70`。

#### ② `value: '2'` vs `value: bar` —— 这个引号**该留**

第一轮我把它归成"多余的引号"去掉了，因为 `Kv.value` 在 schema 里恒是字符串、
解析侧本来就把 `2` 转成 `"2"`，往返等价。**但这个推理漏了读者。**

HTTP 报文里没有数字类型——query / header / 表单的值语义上恒是字符串。裸写 `value: 2`
虽然读得回 `"2"`，但**看的人无从判断它是数字还是字符串**。Postman / Insomnia 的
collection（JSON）里同样是 `"2"`。所以规则是按**字段的语义类型**来，而不是按"能不能读回来"：

| 语义类型 | 写法 | 例 |
|---|---|---|
| 字符串（`value` / `name` / `target` / `url` / `id` / `apicase`） | 数字 / 布尔形态**加引号** | `value: '2'`、`name: '1'`、`apicase: v0.1` |
| 数字 / 布尔（`timeoutMs` / `x` / `y` / `enabled` / `verifySsl`） | 裸写 | `timeoutMs: 500000`、`x: 502` |
| 自由类型（`vars` / `body.json` 的值） | 引号在这里**有语义** | `retries: 3` vs `label: '3'` |

`timeoutMs: 500000` 裸写是因为它在模型里**真的是 `u64`**——写成 `'500000'` 反而误导。

**`assertions[].value` 是个例外，裸写**（`emit.rs` 的 `LOOSE_SUBTREE_KEYS`）。第一版把它
和 `query[].value` 当成同一类，那是把两个同名字段混为一谈了：前者是**期望值**、不进报文、
类型该跟着 `target` 走（`status` 就是数字）；而且它在模型里恒是 `String`、比较本就宽松
（先文本再数字），**引号对结果毫无影响**，强加只是噪声。

> 顺带评估过把 `Assertion.value` 改成 `serde_json::Value` 以保留类型。**没做**：
> 收益在宽松比较下用不上（服务端返 `"2"` 还是 `2` 用户事先不知道，严格比会误报），
> 代价却是可视化断言编辑器多出"输入框里的 `200` 是数字还是字符串"这个歧义。
> 真要做严格类型断言（`strictEq`）时再改不迟——那时输入框才有理由配类型选择器。

**key 位置更宽松**（key 恒按字符串取用、无类型歧义）：读得回原值就裸写，①里的 `y: -70` 靠的就是这条。

**KV 的名字也可能是纯数字**（`?1=2`）。case 用的是 **`name` / `value` 数组**而非 map，
所以参数名在 YAML 里是**值位置**，同样写成 `name: '1'`。这也正是数组形式优于 map 的地方：
参数名可以是任意字符串、可以重复、可以带 `enabled` 与 `description`。

判定用**真实解析器**验证而不是手写判定表——「什么算数字」的边界（`1_000` 是字符串、
`007` 是字符串、`.inf` 是数字）只有解析器自己说了算，手写的表迟早会分叉。
故 `yes` / `no` / `2026-07-30` / `12:30` 这些在 1.2 里本就是字符串的值**不带引号**。

**解析侧宽进、序列化严出**：手写时不必加引号（`value: 2` / `name: 123` / `apicase: 0.1`
都读成字符串），保存时规范化成带引号，把"这是字符串"在文件里写明白。

#### ③ `url: ${{baseUrl}}/get` —— 换变量语法才能去掉

这个引号是 **YAML 语法强制**的：`{` 是流式映射起始指示符。实测三家解析器
（`serde_yaml` / `js-yaml` / YAML 1.2 参考实现 `yaml`）行为一致：

| 写法 | 结果 |
|---|---|
| `url: ${{baseUrl}}/get` | ✗ 语法错误 |
| `url: ${{baseUrl}}` | ✗ **更糟**：静默读成嵌套映射 `${{"baseUrl": null}: null}`，URL 没了 |
| `url: ${{baseUrl}}/get` | ✓ |

同类场景里 **Ansible** 最贴切（playbook 是真 YAML + `${{ }}` 变量），其官方文档原话：
> Ansible uses `${{ var }}` for variables. If a value after a colon starts with a `{`,
> YAML will think it is a dictionary, so you must quote it.

（顺带澄清两个**不成立**的类比：k8s 原生清单不含 `${{ }}`；Helm 的 `${{ }}` 写在 Go 模板文件里，
渲染前根本不是 YAML。）

**而 `$` 不在指示符表里** —— GitHub Actions 用 `${{ }}` 多半就是为此。故本期把变量语法
改为 **`${{var}}`**，`url: ${{baseUrl}}/get` 可以裸写。**旧写法 `${{var}}` 仍然认**
（`resolve_string` 两种都匹配），旧 case 不必改；保留字面量时也保留它原本的写法，
不把 `${{x}}` 悄悄吐成 `${{x}}`。

#### 最终形态

```yaml
apicase: v0.1
name: GET 回显参数
vars:
  retries: 3                 # 数字（自由类型区，引号有语义）
  label: '3'                 # 字符串
steps:
  - id: get
    protocol: http
    request:
      method: GET
      url: ${{baseUrl}}/get  # ← 变量语法带 $，不必加引号
      query:
        - name: foo
          value: bar
        - name: page
          value: '2'         # ← HTTP 值恒是字符串
    assertions:
      - target: status
        op: eq
        value: '200'
ui:
  nodes:
    get:
      x: 502
      y: -70                 # ← key 位置无类型歧义
```

自写 emitter 还顺带修了 `x: 502.0`（坐标是 f64，通用序列化会写出小数点）。
有**黄金测试**用仓库里真实的 case 逐字比对输出。

### 3.7 已有 case 的迁移

`core/examples/migrate.rs`：把工作空间里的 case 一次性升到最新格式（`{{x}}` → `${{x}}`、
`apicase: '0.1'` → `v0.1`），随后经 `parse_case` → `dump_case` 规范化格式。

三点设计：

- **默认预演不写盘**，`--write` 才落地——批量改用户的源文件，先让人看清要改什么。
- **每个文件都做语义等价校验**：迁移前后的模型必须逐字段相同（把"刻意改动的两处"归一化后比对），
  不等价就跳过并提示手工检查。批量改文件不能只靠"我觉得替换是安全的"。
- **幂等**：`upgrade_vars` 跳过已带 `$` 的，重复跑不会变成 `$${{`。

在 `/Users/wanghouping/development/local/apitest` 上的实测结果：**29 个 case 全部迁移成功、
0 跳过**，随后 `run_workspace` 跑出 **29/29 通过、71/71 断言通过**；再跑一次迁移显示"全部已是最新"。
引号总量从 **245 降到 33**（单引号 93 → 31、双引号 152 → 2，剩下那 2 个是 docs 里
英文引文 `"I'm a teapot"` 的一部分）。

### 3.3 HTTP 客户端池（本期最大的性能收益）

按「代理 + 证书校验 + CA + 超时」这组配置缓存 `reqwest::Client`。配置不变就一直复用同一个，
**keep-alive 连接因此能真正活下来**。

CA 文件的 **mtime 与长度**参与缓存键：换了证书文件客户端自动重建，不必重启——
只用路径做键的话，改完证书还得重启才生效，很难想到原因。

有测试钉住：5 个用例打同一个 mock server，服务端只应接受 **1 条** TCP 连接。

### 3.4 并发：实现但默认串行

`concurrency > 1` 时 case 之间用 `tokio::Semaphore` 限流并发，case 内部的 step 仍按拓扑序串行。
**默认仍是 1**，与改造前行为一致。

并发是安全的（case 之间不共享任何上下文），唯一的共享点是 OAuth 2.0 的 token 缓存——
那里做了 **in-flight 去重**：每个缓存键一把异步锁，同键并发只有第一个真去换 token，
其余在锁上等、醒来直接读缓存。没有它，8 个并发就是 8 次 token 交换，既慢又可能触发限流。

串行路径**独立成一支**（不走 spawn 与信号量）：顺序精确、`stopOnFailure` 语义干净，
也省掉调度开销。这是默认路径，风险最低。

### 3.5 进度按增量推

一份跑了 200 个用例的报告可达数 MB。每完成一个就把**整份**序列化过一次 IPC，
光是编解码就能把界面拖卡。

故事件分三种：`start`（报告头，`cases` 为空）→ `case`（逐个追加）→ `end`（收尾）。
前端拿 `start` 打底，之后追加。

> 这里踩到一个真实的坑：`#[serde(rename_all)]` 在 enum 上**只管 variant 名**，
> 字段名要 `rename_all_fields`。少了后者，前端读 `durationMs` 就是 `undefined`，
> 表现为「进度条一动不动」且没有任何报错。已由测试钉住。

### 3.6 报告渲染下沉，且与旧实现逐字一致

`report.ts` 的 CSS / HTML / JS 抽成三个资源文件，由 `include_str!` 编译进二进制。
迁移时做了**逐字比对**：Rust 渲染的空壳与原 TS 版完全相同——历史报告与新报告不会有任何视觉差异。

CLI 因此也能出一模一样的报告。

## 四、性能

| 项 | 改造前 | 改造后 |
|---|---|---|
| HTTP 客户端 | 每请求重建（TLS 根证书库 + 连接池） | 按配置缓存复用 |
| 连接复用 | 无（每请求新连接） | keep-alive（测试钉住：5 请求 1 连接） |
| case 并发 | 不可能（JS 单线程 await 串行） | `Semaphore` 调度，默认 1、可调 N |
| 报文体 | Rust → IPC → JS 解析 → JS 处理 → IPC → Rust 写盘 | 全程在 Rust，不过 IPC |
| 进度事件 | — | 增量推送（而非每次整份） |
| 响应读取 | `text()` 一次性全读 | 分块累加 + 64MB 上限（防 OOM） |
| 发布构建 | 默认 | LTO + 单 CGU |

## 五、过程中修掉的缺陷

改造不是平移，测试与验证抓出了几个**原实现就存在**的问题：

1. **断言的 `actual` 没有脱敏**（安全）。一条 `$.data.token exists` 断言，`actual` 里放的
   就是刚从响应体取出的 token 原文——它既不在请求头、也不在 outputs，原有的四条脱敏规则
   一条都拦不住。补为第五条规则：目标路径像凭据就按名字掩码，否则仍做已知值字面替换。
   占位符 `∅`（路径不存在）与 `—`（无期望值）放过，否则"没这个字段"与"值被藏了"就分不清了。
2. **锁中毒会让功能永久报废**（健壮性）。客户端池若照直 `unwrap`，别处一次无关的 panic
   毒化了锁之后，此后每个请求都以「缓存已损坏」告终。改为取回内部数据继续用——
   池里存的只是可重建的客户端，没有需要保护的不变量。
3. **响应体无上限**（健壮性）。`text()` 一次性全读，误把下载接口当 API 跑会先吃光内存。
   改为分块累加，跨过 64MB 上限即中止并**明确报错**（不静默截断——那会让人对着一份
   缺尾巴的 JSON 排查半天）。
4. **OAuth 2.0 改配置后仍用旧 token**。缓存键补上 `clientSecret`，改任何一项即自动失效，
   前端因此也不必再手动清缓存。

## 八、风险与边界

- **YAML 输出格式变化**：自写 emitter 后，既有 case 文件在**首次保存时**会产生一次格式 diff
  （`'y': -70` → `y: -70`、`x: 502.0` → `x: 502`）。语义完全等价，且是一次性的。
- **变量语法**：新写法 `${{var}}`，旧写法 `${{var}}` 仍然认，故旧 case 零成本继续用。
  但旧 case **不会被自动改写**（那是用户的数据，不该悄悄动）——想去掉 `url:` 那个引号需要
  手工把 `${{` 换成 `${{`，一条 `sed -i 's/${{/${{/g'` 的事，且能在 git diff 里逐处确认。
- **正则语法差异**：断言的 `matches` 从 JS 正则换成 Rust `regex`，后者**不支持环视与反向引用**。
  用到那些的表达式会被判为无效（结果 false）而不是静默乱匹配。实践中断言正则极少用到这些。
- **JSON 报文体的浮点形态**：YAML 里的 `1.0` 会以 `1.0` 发出（JS 的 `JSON.stringify` 发 `1`）。
  JSON 语义等价。
- **并发未进 UI**：`concurrency` 已可用，但运行配置对话框尚未暴露该项，默认恒 1。
- **报告目录仍固定**：`.apicase/reports/<时间戳>/report.html`，输出路径与格式未做成可配。
