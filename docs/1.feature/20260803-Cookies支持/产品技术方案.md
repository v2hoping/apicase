# Cookies：自动收发、持久化与管理

_创建：2026-08-03_

## 需求

### 现状：每个请求都是一座孤岛

apicase 目前把每次 HTTP 往返当成独立事件：响应里的 `Set-Cookie` 没人接住，下一个请求
也不会带 `Cookie`。于是所有**基于 session cookie 的被测服务**都跑不通常规流程——

```yaml
steps:
  - id: login          # 服务端回 Set-Cookie: JSESSIONID=…; Path=/; HttpOnly
    request: { method: POST, url: ${{baseUrl}}/login }
  - id: profile        # 这一步拿不到会话，401
    dependsOn: [login]
    request: { method: GET, url: ${{baseUrl}}/me }
```

现在的绕法是把 cookie 当普通头处理：`outputs` 里从 `res.headers.set-cookie` 提取整串，
下游手写 `Cookie: ${{steps.login.outputs.sc}}` 塞回去。三处不对：

1. **要用户自己做 cookie 解析**。`Set-Cookie` 的值里含 `Path` / `Expires` / `HttpOnly` 这些属性，
   整串塞进 `Cookie` 头是错的（服务端多半仍能容忍，但这已经不是 HTTP 语义了）。
2. **多个 cookie 就塌了**。服务端下发两个 `Set-Cookie` 时，响应头模型（`Vec<KvPair>`）里是两行同名头，
   `res.headers.set-cookie` 只取得到其中一行。
3. **跨 case 不成立**。每个 case 一份独立 `RunContext`（刻意的，见「变量隔离」），
   `outputs` 不跨 case 共享。于是「登录一次、后面十个用例复用会话」这个最常见的回归形态无法表达。

Postman 与 Bruno 的解法是同一个：内置一份 **cookie jar**——自动收 `Set-Cookie`、按域/路径自动回带，
配一个按域分组的管理界面用来查看和清理。本需求就是把这件事补上。

### 决策

| 项 | 选择 | 理由 |
|---|---|---|
| 作用域 | **工作空间级**，存 `<workspace>/.apicase/cookies.json` | 一个工作空间＝一个项目，会话不该跨项目串味；`.apicase/` 已在 `.gitignore`，凭据不会被提交 |
| 开关 | **工作空间设置 `settings.cookies`，默认开** | 与 `verifySsl` / `continueOnAssertionFailure` 同层：随 git 传给团队，回归行为一致。默认开对齐 Postman / Bruno，也对齐浏览器直觉 |
| 管理界面 | 设置页新增「Cookies」分区：**查看 / 删单条 / 清某域 / 清全部** | 覆盖两个真实用途——排查「这次到底带了什么」和「清掉登录态重跑」。手动新增/编辑留后续（见「不做的事」） |

## 方案

### 一、存储：一份 jar，按工作空间分文件

```
<workspace>/.apicase/
├── reports/          # 已有
└── cookies.json      # 本期新增：cookie jar（ndjson，cookie_store 的格式）
```

- **进程内按文件路径缓存 jar**（`HashMap<路径, Arc<CookieJar>>`）：同一个工作空间的所有请求
  共用一份内存 store，切工作空间即换一份。首次使用时惰性从磁盘加载。
- **落盘节流**：cookie 变更只标脏，最快 1s 落一次盘；`flush_all()` 在每次调试运行、
  每轮批量运行收尾时强制写一次。批量跑 200 个用例不该产生 200 次写盘，而关掉应用不该丢会话。
- **会话 cookie（无 `Expires`）一并持久化**。浏览器的语义是"关标签页就丢"，但 apicase 的使用形态是
  「昨天登录过、今天接着调」——这里对齐 Postman 而不是对齐浏览器。已过期的 cookie 加载后不会被发送。

不选**应用全局**一份 jar：两个项目都打 `localhost:8080` 时会互相覆盖对方的会话，
而这在本机开发里是常态。不选**纯内存**：登录态每次重启都要重跑一遍，正是 jar 要消灭的麻烦。

### 二、执行链路：谁在什么时候动 cookie

RFC 6265 的域匹配（`Domain=.example.com` 覆盖子域）、路径匹配、`Secure` / `HttpOnly`
的适用条件、`Expires` 与 `Max-Age` 的优先级这些规则**不自己写**——用 `cookie_store` crate
（reqwest 自己的 `Jar` 用的也是它，版本还恰好同为 0.22，类型直接互通）。自己写这套规则的
错误方式有很多种，而每一种都表现为「某个 cookie 莫名其妙没带上」，极难排查。

> 公共后缀拒绝（不许给 `.com` 整个顶级域设 cookie）需要额外喂一份 PSL 数据，
> 本期与 reqwest 默认行为一致：**不启用**。接口测试打的是已知的被测服务，
> 为此拖一份需要定期更新的域名清单进来不划算。

两个接入点：

1. **发送前**（`auth::send_with_auth` 里 `request::build` 之后）：从 jar 取该 URL 匹配的 cookie，
   拼成 `Cookie: a=1; b=2` 追加进 `req.headers`。
   **用户手写的 `Cookie` 头优先**——显式写了就照它发，jar 不插手（同 Postman 的行为，
   也是"用户显式意图 > 自动行为"的一般原则）。
2. **收响应时**：交给 reqwest 的 `cookie_provider`——我们把同一份 jar 实现成
   `reqwest::cookie::CookieStore` 装进客户端。

第 2 点为什么不自己在响应回来后解析 `Set-Cookie`：**重定向链**。登录接口的典型形态是
`POST /login → 302 + Set-Cookie → GET /home`，中间那一跳的响应我们根本看不到
（reqwest 内部就跟完了），自己解析等于漏掉最关键的那个 cookie；而且重定向后的那一跳
也需要带上刚拿到的 cookie。装 provider 后这两件事由 reqwest 在链路内部完成。

**报告仍如实**：第 1 点自己把 `Cookie` 头写进了 `req.headers`，报告里因此看得到本次实际带出的 cookie
（reqwest 只在请求没有 `Cookie` 头时才由 provider 补，两条路径不会打架）。这与
「报告存真实值、`send_with_auth` 返回实际发出的那一份请求」是同一条原则——
认证与会话恰恰是最常出问题的两环，报告里看不见就等于没法排查。

**客户端池**：`ClientKey` 增加 jar 标识（开关 + jar 路径）。cookie provider 是 builder 级设置，
不进缓存键就会出现「关了开关仍在带 cookie」这类跟着缓存走的幽灵行为。

### 三、开关：`settings.cookies`

```yaml
settings:
  cookies: false        # 默认 true，故只有关闭时才落盘
```

- 解析容错同其它项：**只有显式 `false` 才关闭**，键缺失 / 写错类型都按开启。
- 关闭时：不带 cookie、不收 `Set-Cookie`，但**已存的 `cookies.json` 保留**——
  关开关是"这轮不要自动带"，不是"删掉我的会话"。管理界面照常可看可清。
- 前端 `ClientConfig` 增加 `cookies: { enabled, jarPath }`，与 `caCertPath` 同样由前端
  把相对路径还原成绝对路径后下发（core 不猜工作空间在哪）。

顺手修一个既有缺陷：`dump_application_config` 清理旧键时漏了 `continueOnAssertionFailure`，
导致该项从 `true` 改回 `false` 时旧值残留在文件里（写回的是 `ser_settings` 的产出，
而默认值不落盘，于是没有键去覆盖它）。本期把受管键收成一份常量数组，新加的 `cookies` 同样是默认值不落盘、
关闭才写 `false`，会踩同一个坑。

### 四、管理界面：设置页 →「Cookies」

放在导航的**项目组**（「通用 / 环境」之后、分割线之前）——它跟着工作空间走，与主题/代理那些应用级偏好不同层。

```
┌ Cookies ───────────────────────────── [清空全部] ┐
│ api.example.com                        [清空该域] │
│   ▸ JSESSIONID  =  9F2A…C31   /   会话   Secure HttpOnly  [×] │
│   ▸ locale      =  zh-CN      /   2026-09-01              [×] │
│ localhost                              [清空该域] │
│   ▸ token       =  eyJhbGciOi…                            [×] │
└──────────────────────────────────────────────────┘
```

- 按域分组，组内按 name 排序；显示 name / value / path / 过期时间（无则「会话」）/ `Secure` / `HttpOnly` 标记。
- 值**不掩码**（同报告的既有决策：这是排查材料，掩掉的恰恰是要核对的东西），但超长值截断显示。
- 删除单条、清某域、清全部；清空类操作走既有的 `useConfirm` 二次确认。
- 空态："暂无 Cookie。开启后，请求收到的 Set-Cookie 会自动记录在这里。"
- 「通用 → 位置」补一行 Cookie 存储位置（同报告目录那行），否则用户无从知道它在哪。

### 五、命令层

新增三个纯转发命令（语义仍在 core）：

| 命令 | 说明 |
|---|---|
| `list_cookies(jarPath)` | 读回全部 cookie（按域 + 名排序），供管理界面渲染 |
| `delete_cookie(jarPath, domain, path, name)` | 删一条（三元组才是 cookie 的主键，只给 name 会误删同名不同域的） |
| `clear_cookies(jarPath, domain?)` | `domain` 给了清该域，否则全清 |

#### 七、管理界面二期：增删改查（2026-08-03 追加）

初版只做了「查看 + 删除 + 清空」，实际用下来还是要能手工塞一个 session 进去调试，故补齐。
版式**读了 Bruno 的源码**（`packages/bruno-app/src/components/Cookies/index.js`）之后对齐，它的形态是：

| Bruno 的做法 | 我们 |
|---|---|
| 域是 **Accordion**，`defaultIndex={0}` 只展开第一个 | 同（记在 `openDomains`，没记过的按「第一组展开」） |
| 域头：域名 + `(N cookies)` + **＋ / 🗑** 两个操作 | 同（计数写成 `N 个`；两个操作 hover 该组才浮出） |
| 展开后是**表格**：Name / Value / Path / Expires / Secure / HTTP Only / Actions | 同，另加**子域**列（见 `hostOnly`）；Secure 类用 `✓` 居中 |
| 单元格截断 + tooltip 给全文 | 同（`title`） |
| 空态：大图标 + 标题 + 副文案 + 「Add Cookie」 | 同（饼干图标）；搜不到时另给一套（放大镜 + 「清空搜索」） |
| 搜索**只按域名** | 域 / 名 / 值一起搜 —— 「哪个 cookie 存着这个 token」同样常见 |
| 编辑弹窗：除过期与复选框外**两列网格**；`domain/path/key` 编辑时禁用 | 两列同；**主键可改**（后端按 `prev` 删旧的，见下），不必删了重建 |
| 删除 / 清空都有确认弹窗 | 同（复用既有 `useConfirm`） |

操作一律图标按钮（`.icon-btn`：常态低调、hover 才浮出底色）——密集列表里文字按钮每行都要占掉一截宽度。
- **增改是同一个入口**（`CookieJar::put` + `save_cookie` 命令）：拼一行 `Set-Cookie` 交给解析器，
  而不是自己拼装属性对象——手工加的与服务端下发的因此走同一套合法性判定。
  改了域 / 路径 / 名要按 `prev` 删掉原来那条，否则留下孤儿。
  `Expires=` 需要 HTTP 日期，为此给 `util` 补了 `http_date`（自算历法，同 `iso8601` 不引时区库）。
- **校验只在 Rust**，前端把错误原样显示在对话框里、不关窗，不复刻一份必然漂移的判定。
- **`hostOnly` 单独暴露**：store 里 host-only 与带 `Domain` 属性的域名字符串长得一样，
  不标出来的话编辑一次就把「子域一并生效」悄悄丢了；编辑框用 `.example.com` 的写法表达它。

## 六、不做的事（本期边界）

- **响应区 Cookies 标签页**：`Set-Cookie` 已经在响应头里看得到，先不新增一个只做重排的视图。
- **case / step 级的 cookie 开关**：先只有工作空间一级。粒度做细容易，收回来难。
- **cookie 的变量替换**：jar 里的值是服务端下发的原文，不参与 `${{}}` 语义。

## 执行计划

1. **依赖**：workspace 根加 `cookie_store`；`reqwest` 开 `cookies` feature。
2. **core `cookie.rs`**（新模块）：`CookieJar`（store + 脏标记 + 落盘节流）、jar 注册表、
   `reqwest::cookie::CookieStore` 实现、`list / remove / clear / flush_all` 管理 API。
3. **core 接线**：`ClientConfig` 加 `cookies`；`ClientKey` 加 jar 标识；`build_client` 装 provider；
   `send_with_auth` 发送前补 `Cookie` 头（用户手写优先）。
4. **core `model/yaml`**：`WorkspaceSettings.cookies`（默认 true）+ 解析 / 序列化 / 受管键数组修缺陷。
5. **命令层**：`commands/cookies.rs` 三个命令 + `lib.rs` 注册；运行收尾处 `flush_all`。
6. **前端**：`case.ts`（设置字段）、`run.ts`（ClientConfig）、`cookies.ts`（IPC 封装）、
   `App.tsx`（开关 + 「Cookies」分区 + 位置行 + clientConfig 组装）、`App.css`。
7. **测试**：
   - core：开关关闭不带 cookie / 收 `Set-Cookie` 后下一个请求带上 / 用户手写 `Cookie` 头不被覆盖 /
     持久化往返 / 删除与清空 / 域隔离（A 域的 cookie 不发给 B 域）。用既有 `MockServer`（真发请求）。
   - yaml：`cookies: false` 的解析与落盘、默认值不落盘、`continueOnAssertionFailure` 关闭后不残留。
   - 前端：设置默认值；`check-ipc.py` 自动核对三个新命令。
8. **文档**：同步 `docs/0.latest/`（技术架构的执行链路与命令表、YAML 规范的 settings 表、概览的能力边界）。
