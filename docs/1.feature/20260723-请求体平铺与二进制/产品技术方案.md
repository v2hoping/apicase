# 请求体：类型平铺 + XML/Binary 补全 + multipart 真发送

_创建：2026-07-23_

## 需求

请求体面板此前是一个下拉（`none / json / text / form-urlencoded / form-data`），
需要美化并补全类型。形态上有两种主流做法：

- **Postman**：`none / form-data / x-www-form-urlencoded / raw / binary`，选 `raw`
  后再出一个二级下拉选 Text / JavaScript / JSON / HTML / XML。
- **Apifox**：`none / form-data / x-www-form-urlencoded / JSON / XML / Text / Binary`，
  把 raw 里的语言平铺到一级。

**取 Apifox 形式**，理由：

1. **少一层点击**：调试里绝大多数是 JSON，一级直达。Postman 的 `raw + 语言` 是历史包袱——
   raw 本就是「原始文本」，语言只影响高亮与 Content-Type，并非真正的两级语义（Postman
   后来也把当前语言显示在 raw 旁边，说明二级藏得过深）。
2. **一眼可见当前请求发的是什么体**，不用展开二级确认。
3. **与本项目数据模型一致**：`BodySpec.type` 本就是平铺的（YAML 里写 `type: json`）。
   若走 Postman 形式，UI 还得维护一层 `raw + language ↔ type` 的映射，凭空造出一个
   模型里不存在的概念。

顺带补齐两处缺口：**新增 XML / Binary 类型**；**form-data 此前是「假功能」**——UI 可选、
可保存，但 `buildApiRequest` 根本不组装 body（注释写着「multipart 发送暂未实现」），
选了发出去是空体。既然 Binary 要动后端，multipart 一并做掉。

## 方案

### 一、类型平铺（UI）

`BodyPanel` 顶部一排 chip（`.body-type-chips`，`flex-wrap` 让窄面板自动换行），顺序与
命名对齐 Apifox：`none / form-data / x-www-form-urlencoded / JSON / XML / Text / Binary`。
选中态用 accent 实底。

其下固定一行 **Content-Type 行**，把「这个体最终发什么头」摆明：
`text` / `binary` 是可编辑输入框（前者默认 `text/plain`，后者不填则不发该头），
其余为只读展示（`form-data` 显示「multipart/form-data（boundary 自动生成）」）。

编辑区按类型切换：`json/xml/text` → textarea；`form-data / x-www-form-urlencoded` → `KVTable`；
`binary` → 文件选择行（`plugin-dialog` 的 `open` 选单文件，显示路径 + 垃圾桶清除，
路径过长时 `direction: rtl` 截前保后——文件名比目录前缀重要）。

### 二、Content-Type 默认值

`draft.ts` 导出 `DEFAULT_CONTENT_TYPE`：`json → application/json; charset=utf-8`、
`xml → application/xml; charset=utf-8`、`text → text/plain; charset=utf-8`、
`form-urlencoded → application/x-www-form-urlencoded`。
**手填的 Content-Type 请求头优先级最高**，默认值仅在未手填时补（原实现里 text 类型
不填 contentType 就完全不发该头，现在给了默认）。文本类**显式带 `charset=utf-8`**——
对齐新版 Postman：body 本就以 UTF-8 字节发送，声明 charset 规避 `xml`/`text`
「无 charset 参数时默认非 UTF-8」的历史坑（RFC 3023），接收端稳解中文；
`form-urlencoded` 的值经 `encodeURIComponent` 已是纯 ASCII 百分号编码，无需 charset。

**binary 对齐 Postman**：不用固定默认，而是 `guessContentType(path)` 按文件扩展名推断
（约 30 种常见类型：图片 / 文档 / 压缩 / 音视频 / Office…），推不出兜底
`application/octet-stream`；手填仍可覆盖。UI 的 Content-Type 输入框 placeholder 实时
显示按当前文件推断出的值，所见即所发。

### 三、Binary 与 multipart（后端）

`ApiRequest` 增两个字段，请求体**三选一**（优先级 `form_data` > `body_file` > `body`）：

- `body_file: Option<String>` —— binary：后端 `std::fs::read` 读盘发原始字节。
  **不把字节塞进 IPC**（大文件搬运代价高），前端只传路径；读不到给
  「读取请求体文件失败（路径）: …」的可读错误。
- `form_data: Option<Vec<FormField>>` —— form-data：交 `reqwest::multipart::Form` 组装。
  `.multipart()` 放在 `.header()` 之后调用，让 reqwest 生成的 `Content-Type`
  （含 boundary）覆盖用户手填的同名头——手填 boundary 必错。
  `reqwest` 需启用 `multipart` feature。

`ApiRequest` 派生 `Default`，Rust 测试改用 `..Default::default()`，以后加字段不再破坏测试。

### 四、数据模型

- `BodyType` 扩为 `none | json | xml | text | form-urlencoded | form-data | binary`。
- `BodySpec` 增 `xml?: string`（同名子键）与 `filePath?: string`（binary）；
  `contentType` 适用范围由 text 扩到 text + binary。
- `ReqDraft` 增 `bodyFilePath`；`xml` 复用 `bodyText` 编辑文本。
- 空内容不落盘：空 `xml`、未选文件的 `binary` 与原有规则一致地被裁剪。
