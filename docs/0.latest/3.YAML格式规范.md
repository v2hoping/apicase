# case YAML 格式规范

> 定义 apicase 的 case 文件（`.yml`）与工作空间配置（`application.yml`）的 YAML 格式。
> **schema 单一事实源在 `app/src/case.ts`**（`parseCase` / `dumpCase`）；本文与其保持一致。

## 总览

一个 `.yml` 文件即一个 case，模型上是一个 **DAG**：单请求 = 单节点 DAG，多请求 = 多节点 DAG（节点间以 `dependsOn` 声明依赖）。写盘时**恒定使用 `steps:` 列表**（单节点也是长度为 1 的列表）；每个 step 用 `protocol:` 显式声明协议，报文承载于 `request:`。

```yaml
apicase: v0.1          # 版本标识（必填，缺省按 "0.1")
name: 用户登录并下单       # 可选：case 名称
vars:                   # 可选：case 级变量（覆盖 environment）
  baseUrl: https://api.example.com
steps:                  # 必填：至少 1 个 step
  - id: login
    protocol: http      # 协议标识（当前仅 http）
    ui:                 # 可选：画布坐标等前端属性（未拖拽过则缺省，按 dependsOn 自动布局）
      x: 40
      y: 40
    request:            # 报文（随 protocol 而定；http 见下）
      method: POST
      url: ${{baseUrl}}/login
      body:
        type: json
        json: { username: admin, password: "123456" }
    outputs:
      token: res.body.data.token
    assertions:
      - { target: res.status, op: eq, value: "200" }
    docs: |             # 可选：该 step 的 markdown 文档
      登录接口，成功后从响应体提取 token 供下游使用。
  - id: createOrder
    protocol: http
    ui:
      x: 40
      y: 200
    dependsOn: [login]
    request:
      method: POST
      url: ${{baseUrl}}/orders
      headers:
        - { name: Authorization, value: Bearer ${{steps.login.outputs.token}} }
      body:
        type: json
        json: { sku: A-1001, qty: 2 }
    assertions:
      - { target: res.body.code, op: eq, value: "0" }
```

## 顶层字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `apicase` | string | 是 | 格式版本，当前 `"0.1"`。 |
| `name` | string | 否 | case 显示名。 |
| `vars` | map | 否 | case 级变量；优先级高于 environment。 |
| `steps` | list | 是 | step 列表，至少 1 个。 |

顶层没有 `ui:` 块——画布坐标挂在各 step 的 `ui:` 上（见下）。

## step（请求节点）

字段书写顺序（与 `dumpCase` 对齐）：`id → protocol → ui → dependsOn → request → outputs → assertions → docs`。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | 节点唯一标识，被 `dependsOn` 与 `${{steps.<id>...}}` 引用；改名需同步引用。 |
| `protocol` | string | 是 | 协议标识，当前仅 `http`；缺省按 `http`。 |
| `ui` | object | 否 | 前端属性，当前只有画布坐标 `{ x, y }`。未拖拽过则省略（按 `dependsOn` 自动布局）。 |
| `dependsOn` | string[] | 否 | 上游依赖的 step `id`；据此自动分层布局与拓扑序执行。空则省略。 |
| `request` | object | 是 | 报文（随 `protocol` 而定）；`http` 报文见下。 |
| `outputs` | list | 否 | 从响应提取变量供下游引用（路径写法同断言目标）。空则省略。 |
| `assertions` | list | 否 | 响应断言。空则省略。 |
| `docs` | string | 否 | 该 step 的 markdown 文档（请求编辑器「文档」标签）。空则省略。 |

### request（http 报文）

`protocol: http` 时 `request` 的字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `method` | string | GET / POST / PUT / DELETE… |
| `url` | string | 请求 URL，可含 `${{var}}`；query 与 url 双向同步。 |
| `query` | KV[] | 查询参数（UI「参数」页），空则省略。 |
| `headers` | KV[] | 请求头，空则省略。 |
| `auth` | object | 认证，`type: none` 时省略。 |
| `body` | object | 请求体，`type: none` 或空时省略。 |

**KV** 结构：`{ name, value, enabled?, description? }`。`enabled` 默认 `true` 且省略，仅关闭某行时写 `enabled: false`；`description` 为可选备注（对应 UI「参数 / 请求头 / 表单」表格的「描述」列），空则省略、不影响实际请求。

### auth（认证）

`type` 取值：`none` / `bearer` / `basic` / `apikey` / `digest` / `oauth2`，对应子对象二选一
（UI 显示名对齐主流工具：No Auth / Bearer Token / Basic Auth / API Key / Digest Auth / OAuth 2.0）：

```yaml
auth: { type: bearer, bearer: { token: ${{token}} } }
auth: { type: basic,  basic:  { username: admin, password: "123456" } }
auth: { type: apikey, apikey: { key: X-Api-Key, value: ${{apiKey}}, in: header } }  # in: header | query
auth: { type: digest, digest: { username: admin, password: ${{password}} } }        # 摘要按 401 challenge 现算
auth:
  type: oauth2                       # 仅客户端凭据模式（client_credentials）
  oauth2:
    tokenUrl: https://auth.example.com/oauth/token
    clientId: ${{clientId}}
    clientSecret: ${{clientSecret}}
    scope: read write                # 可选，空格分隔；空则省略
    clientAuth: body                 # 凭据位置：header（Basic 头，默认，省略不写）| body（表单体）
```

`digest` / `oauth2` 的凭据不会直接写进请求头：前者要先拿服务端 401 的
`WWW-Authenticate` challenge 才能算摘要，后者要先向 `tokenUrl` 换 `access_token`
（按 `tokenUrl|clientId|scope|clientAuth` 缓存、提前 30s 过期）。两者的额外请求同样
走后端并复用代理设置。

### body（请求体）

`type` 取值：`none` / `form-data` / `form-urlencoded` / `json` / `xml` / `text` / `binary`
（UI 平铺成一排，顺序同上；不做 Postman 那层 `raw` + 语言二级下拉）。

```yaml
body: { type: json, json: { a: 1, b: "x" } }              # 结构化对象，diff 友好
body: { type: xml,  xml: "<root><a>1</a></root>" }        # 原文文本
body: { type: text, text: "raw...", contentType: text/csv } # contentType 可选，覆盖默认 text/plain
body: { type: form-urlencoded, urlencoded: [ { name: a, value: "1" } ] }
body: { type: form-data, formData: [ { name: a, value: "1" } ] }  # 每项可为文本 / 文件，见下
body: { type: binary, filePath: ./avatar.png, contentType: image/png }  # contentType 可选
```

**默认 Content-Type**（未在 `headers` 手填时自动补，手填优先）：`json` → `application/json; charset=utf-8`、
`xml` → `application/xml; charset=utf-8`、`text` → `text/plain; charset=utf-8`（可用 `contentType` 覆盖）、
`form-urlencoded` → `application/x-www-form-urlencoded`（值经百分号编码，无需 charset）；
`form-data` 由后端 reqwest 生成（含 boundary）；`binary` **按文件扩展名推断**
（`.png`→`image/png`、`.pdf`→`application/pdf`…，推不出兜底 `application/octet-stream`，同 Postman），
`contentType` 手填则覆盖推断值。文本类显式带 `charset=utf-8`（对齐新版 Postman）——
body 本就以 UTF-8 字节发送，声明 charset 规避 xml/text「无 charset 默认非 UTF-8」的历史坑。

`binary` 的 `filePath` 指向本地文件，**发送时由后端读盘、以原始字节作为请求体**；文件不存在时报可读错误。

**form-data 的文件字段**：`formData` 的每项在 `name / value / enabled / description` 之外
可带 `type`（`text` 默认、不落盘 | `file`）。`type: file` 时 **`value` 即本地文件路径**
（不另立子键——行结构与其它键值表一致，禁用、备注、`${{变量}}` 替换全部复用；
形态对齐 Postman 的 `{key, type: "file", src}`）：

```yaml
body:
  type: form-data
  formData:
    - { name: title, value: 头像 }                    # 文本字段
    - { name: file, type: file, value: ./avatar.png } # 文件字段，作为一个 multipart part 上传
```

该 part 的 `filename` 取路径文件名、`Content-Type` 按扩展名推断（同 `binary` 那张表，
兜底 `application/octet-stream`），均无需手写。文件同样**由后端读盘**，读不到时错误信息带字段名与路径。
一行一个文件；要发同名多 part，再加一行同名字段即可。

### outputs（输出提取）

map 结构 `{ 变量名: 路径 }`：键为变量名，值的写法**与断言目标完全相同**（`res.status` / `res.headers.<名>` / `res.body<路径>`），提取的值供下游 `${{steps.<id>.outputs.<变量名>}}` 引用。

```yaml
outputs:
  token: res.body.data.token
  orderId: res.body.data.id
  traceId: res.headers.X-Trace-Id     # 响应头同样可提取
```

### assertions（断言）

列表项结构 `{ target, op, value? }`：

- **`target`**：断言目标，**统一挂在 `res` 命名空间下**（认不出的目标一律取不到值，
  结果表的「实际」列显示 `∅`）：

  | 写法 | 取到 |
  |---|---|
  | `res.status` | 状态码 |
  | `res.headers.<名>` / `res.headers['<名>']` | 响应头（名字大小写不敏感） |
  | `res.body` | 整个响应体（非 JSON 响应给原文，可做 `contains` / `matches`） |
  | `res.body<路径>` | 响应体内路径，`.key` / `[n]` / `['key']`（JSONPath 常用子集） |

- **`op`**：`eq` / `ne` / `contains` / `exists` / `notExists` / `gt` / `lt` / `matches`。
- **`value`**：期望值；`exists` / `notExists` 无需 value（省略）。

```yaml
assertions:
  - { target: res.status, op: eq, value: "200" }
  - { target: res.headers.Content-Type, op: contains, value: application/json }
  - { target: res.body.data.token, op: exists }
  - { target: res.body.list[0].id, op: eq, value: "1" }
```

`res.` 前缀是唯一写法——`status`、`header.X`、`$.data.token` 这些**旧写法不再识别**。
统一命名空间对齐了同类工具的直觉（Bruno 的 `res.*`、Postman 的 `pm.response.*`），
也让请求编辑器能按最近一次响应逐层提示路径与当前值。

**`outputs` 与断言共用这套写法**（见上一节）：两者做的是同一件事——从这次响应里取一个值。
统一之后输出不再限死在响应体内，`res.headers.Set-Cookie`、`res.status` 都能直接提取
（旧的 `$.` 写法做不到）；编辑器里两处也共用同一个带补全的输入框。

### ui（前端属性）

```yaml
ui:
  x: 502
  y: -70
```

**为什么挂在 step 上**：坐标早先存在顶层 `ui.nodes.<stepId>`，是一张与 `steps:` 并行的
id 映射表——改个 id 要动两处、删个 step 会在那边留下孤儿坐标、diff 里也看不出坐标属于谁。
挂进 step 之后这三件事自然消失。旧的顶层 `ui:` 块**不再识别**（坐标丢失、回退自动布局），
用 `core/examples/migrate.rs` 批量转。

**写法与别处一致**：一行一个字段的块式，不给坐标开流式（`{ x, y }`）的小灶——
全文件一套写法，读的人不必在两种风格间切换，输出器也不必为此多一条按 key 的例外规则。

坐标写坏了（缺 `x`、值不是数字）只丢坐标、回退自动布局，不会让整条用例解析失败——
它是视图态，不该有能力废掉一条用例。将来的前端属性（折叠、配色…）也加在这个键下面。

### docs（step 文档）

`docs` 为一段 markdown 文本，在请求编辑器「文档」标签中编辑与预览（支持标题、列表、代码块、表格、引用、链接、图片等）。空则不落盘。

## 变量与透传

- **语法**：`${{name}}`；跨节点引用上游输出用 `${{steps.<step id>.outputs.<输出名>}}`。
  **只认这一种写法**——无 `$` 的 `{{name}}` 不再替换（原样发出去）。
- **为什么带 `$`**：`{` 是 YAML 的流式映射起始指示符，以 `${{` 开头的值必须整行加引号
  （`url: ${{baseUrl}}/get`，不加是语法错、`url: ${{host}}` 更会被静默读成嵌套映射）；
  而 `$` 不在指示符表里，`url: ${{baseUrl}}/get` 可以裸写。GitHub Actions 用 `${{ }}` 多半同理。
  同类工具里 Ansible 用 `${{ }}` 且其官方文档明确要求加引号——我们换个前缀就免了这道。
- **来源与优先级**（就近覆盖）：environment（`application.yml`）< case 级 `vars` < 上游节点 `outputs`。
- 未解析到的 `${{var}}` **保留字面量**（发送时不报错，且保留它原本的写法）。

## 序列化约定（dumpCase）

- 恒定写 `steps:` 列表（单节点 = 长度 1）；**读取仅认此格式** —— 旧格式（`requests:` 列表、`http:` 报文键）不再兼容，可视化编辑器会将其判为无效 case 并回退为纯文本编辑。
- 裁剪默认值：`enabled: true`、`formData` 项的 `type: text`、空 `query/headers/outputs/assertions/dependsOn`、`body.type=none`、`exists/notExists` 的 `value`、空 `docs`、空 `description`、无坐标的 `ui` 均不落盘。
- `json` body 以结构化对象存储（便于 diff），而非转义字符串；对象与 `vars` 的**键序按书写顺序保留**，不做字母重排。

### 引号规则：按字段的语义类型

序列化由执行内核自己的输出器完成（`core/src/yaml/emit.rs`），不用通用库——落盘的 case 是
用户要读、要 diff、要 review 的源文件，格式不是实现细节。

**一条规则：值位置的字符串，裸写后若不被读成字符串就加引号。**
数字 / 布尔字段本来就是数字 / 布尔值，天然裸写。

| 字段的语义类型 | 写法 | 例 |
|---|---|---|
| **字符串**（`value` / `name` / `target` / `url` / `id` / `apicase` …） | 数字 / 布尔形态的值**加引号** | `value: '2'`、`name: '1'`、`apicase: v0.1` |
| **数字 / 布尔**（`timeoutMs` / `x` / `y` / `enabled` / `verifySsl`） | 裸写 | `timeoutMs: 500000`、`x: 502`、`enabled: false` |
| **自由类型**（`vars` / `body.json` 的值） | 由用户决定，引号在这里**有语义** | `retries: 3`（数字）vs `label: '3'`（字符串） |

为什么 `value: '2'` 要带引号：HTTP 报文里没有数字类型，query / header / 表单的值语义上恒是字符串。
裸写 `value: 2` 虽然也读得回 `"2"`，但读的人无从判断它是数字还是字符串。
Postman / Insomnia 的 collection（JSON）里同样是 `"2"`。

而 `timeoutMs: 500000` 裸写，是因为它在模型里**真的是数字**（`u64`）——写成 `'500000'` 反而误导。

**`assertions[].value` 为什么裸写**：它是**期望值**、不进 HTTP 报文，类型该跟着 `target` 走
（`res.status` 就是数字，写 `value: 200` 才自然）。而且断言的比较本就是宽松的——
`value` 在模型里恒是 `String`（YAML 的 `200` 与 `'200'` 解析后都是 `"200"`），
比较时先按文本、再按数字试一遍，**引号对结果毫无影响**。既然如此就不该强加。

这也意味着期望值写字符串一样工作：`value: ok`、`value: true` 都读成字符串，
按同一套宽松规则比较。服务端把 `page` 返成 `"2"` 还是 `2`，`value: 2` 都能匹配上——
这是刻意的，否则会因为服务端的类型选择而误报，而那跟被测接口对不对没关系。

**key 位置更宽松**：key 永远按字符串取用，不存在类型歧义，只要读得回原值就裸写。
画布坐标的 `y: -70` 正是靠这条不带引号（YAML 1.1 会把 `y` 当布尔别名，1.2 不会，我们按 1.2）。

**KV 的名字也可能是纯数字**（`?1=2` 这种）。case 用的是 **`name` / `value` 数组**而不是
map，所以参数名在 YAML 里是**值位置**（`name:` 才是 key），同样按上表处理写成 `name: '1'`。
这也是数组形式优于 map 形式的地方：参数名可以是任意字符串、可以重复、可以带 `enabled` 与 `description`。

**宽进严出**：手写时不必加引号（解析侧一律把标量转字符串，`value: 2` / `name: 123` /
`apicase: 0.1` 都读成字符串），保存时规范化成带引号。

判定用**真实解析器**验证，不是手写的判定表——"什么算数字"的边界（`1_000` 是字符串、
`007` 是字符串、`.inf` 是数字）只有解析器自己说了算。因此 `yes` / `no` / `y` / `2026-07-30` /
`12:30` 这些在 YAML 1.2 里本就是字符串的值**不带引号**。

**单引号还是双引号**：YAML 两种都合法但语义不同——单引号是字面量（唯一转义是把 `'` 写两遍，
**反斜杠原样**），双引号是唯一能表达任意字符串的风格（支持 `\n` / `\t` / `\uXXXX`）。
规范没有"推荐哪个"，各家默认也不同（`js-yaml` 与 `serde_yaml` 默认单引号，YAML 1.2 参考实现
`yaml` 默认双引号）。apicase **默认单引号、只在单引号表达不了时（含控制字符）升级到双引号**——
要加引号的值里常含反斜杠（断言的 `matches` 正则、Windows 路径），双引号会逼着把 `\d` 写成 `\\d`。

其余格式约定：多行文本走块标量（以换行结尾用 `|`，否则 `|-`）；序列缩进一级
（`steps:` 下面是 `  - id: …`）；整数值的坐标写成整数（不留 `502.0`），
真浮点保住小数点（`1.0` 不写成 `1`）。

> 既有 case 首次保存时会有一次格式 diff（`'y'` → `y`、`502.0` → `502`、
> 变量语法 `${{x}}` 保持原样不动），语义完全等价。

## application.yml（工作空间配置）

工作空间根目录的配置文件，含多套 environment 与工作空间级请求设置：

```yaml
environment:
  dev:  { baseUrl: https://dev.example.com,  token: "" }
  prod: { baseUrl: https://api.example.com,  token: "" }
settings:                 # 可选：请求设置（「设置 → 通用」，全为默认时整键不落盘）
  verifySsl: false        # SSL/TLS 证书验证，默认 true
  useCustomCa: true       # 是否启用自定义 CA，默认 false
  caCert: certs/ca.crt    # CA 证书路径，相对工作空间根
  timeoutMs: 30000        # 请求超时（毫秒），默认 0 = 不限制
```

topbar 右侧下拉切换活动环境，运行时注入变量（值统一转字符串）。详见 [2.技术架构](2.技术架构.md)。

### settings（请求设置）

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `verifySsl` | bool | `true` | 校验服务端证书的签发链、有效期与域名/IP 匹配。**仅显式 `false` 才关闭**——键缺失或类型写错都按开启这一安全侧兜底 |
| `useCustomCa` | bool | `false` | 是否启用 `caCert`。**仅显式 `true` 才启用**；关闭时保留 `caCert` 的值，便于再次打开时不必重选 |
| `caCert` | string | `""` | CA 证书文件，**相对工作空间根**（绝对路径换机器就失效，相对路径随仓库走）。支持 `.pem/.crt/.cer/.der/.ca-bundle` |
| `timeoutMs` | number | `0` | 请求超时上限；`0`、负数、非数字一律视为不限制，小数向下取整 |

要点：

- 三项对**单请求与流程执行同时生效**（两者共用后端 `send_request` 通道）。
- **写默认值的键不落盘**（同 case 序列化的裁剪风格）；全为默认时整个 `settings` 键删除，不给既有配置添噪。
- `verifySsl: false` 是**降安全**设置且随 git 传播给团队：流量仍加密，但无法确认对端身份，且请求照常返回 200 而**没有任何异常提示**。更推荐只配 `caCert`——只放行你指定的那一个签发者，其余请求仍完整校验。
- 即便配对了 CA，证书本身仍须满足 rustls 的要求：**必须有 SAN**（只有 CN 的老证书会被拒）、用 IP 访问需 IP 型 SAN、未过期、作为 CA 的证书带 `basicConstraints=CA:TRUE`。这些不是本设置能绕过的。
